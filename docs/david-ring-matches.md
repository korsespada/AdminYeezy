# Развязка дублей колец Chromoff и David Studio

Раздел: `/admin/chromoff/david-rings` — поиск старых колец Chromoff, к которым
подходит модель из выгрузки David, и объединение пары в одну карточку.

## Почему каноном остаётся старое кольцо

Старое кольцо уже опубликовано: у него живой URL `/product/<legacy_slug>`, история
индексации и цена. Карточка David на ту же модель — дубль: цена 0 («цена по
запросу»), а `indexing_status: noindex` задумывался как защита от поиска.

Практика 2026-09 показала, что защиты не хватало: публичный API Chromoff отбирает
листинги по `published` и `Product.active`, а `indexing_status` в витрине не
читался вовсе — дубли попадали и в sitemap, и в индекс. Поэтому в chromoff.store
добавлено соблюдение статуса (`isIndexableProduct`): товары с
`indexing_status != 'indexable'` не попадают в sitemap и получают meta robots
`noindex`.

Удалять старую карточку нельзя: `products#destroy` и `chromoff/listings#destroy`
в Rails не создают `SeoRedirect`, поэтому проиндексированный URL начал бы отдавать
404. А занять исторический slug новым товаром не даёт
`Catalog::ProductSlugRedirector` (`HistoricalSlugReuse`).

## Как работает подбор

```text
старые кольца категории koltsa ─┐
                                ├─→ отбор кандидатов по названию и модели
кольца David из выгрузки ───────┘        │
                                         ▼
             контактные листы: фото товара + плитки эталонов
                                         │
                                         ▼
                        BYESU (модель из «Настроек ИИ») → JSON
                                         │
                                         ▼
                      david_ring_matches (вердикт, кандидаты, статус)
                                         │
                                         ▼
                     экран ревью: применить / отклонить / заменить модель
```

### Отбор кандидатов (без ИИ)

`rankRingCandidates` сравнивает токены названия, атрибута `model_name`, артикула и
slug старого товара с названием и handle кандидатов. Вес токена обратен числу
кандидатов, в которых он встречается, поэтому «Dagger Heart» решает, а «кольцо из
серебра» — почти нет. Токены названия весят больше, чем токены handle: служебное
`chrome-hearts-*-ring` есть у каждого кандидата.

Токены канонизируются: нижний регистр, ё → е, отсечение латинского «s» и усечение
до 5 символов («крестами»/«кресты» → «крест»). Пара без единого общего токена не
возвращается: такие кольца честнее показать как «нет кандидатов», чем гнать
модель по случайным.

На каталоге 2026-09 (146 старых колец, 105 моделей David) кандидаты находятся у
132 колец; очевидные пары (Keeper, Pentagon BS Fleur, Fuck You 6mm, Foti Harris)
стоят в коротком списке первыми, спорные (спиннеры, «с крестами») ИИ выбирает из
шести.

### Решение ИИ

Один вызов на кольцо: контактный лист фотографий товара (до 9 кадров) и
эталонные листы, где i-й эталон занимает три плитки. Промпт перечисляет эталоны с
handle, названием и общими словами. Модель возвращает **индекс** эталона, а не id:
индекс код превращает в handle сам, поэтому галлюцинация не может указать на
посторонний товар. Индекс вне списка сохраняется как статус `invalid_index`, а не
как пара.

Правила промпта: совпадением считается только та же модель; другой цвет камня,
покрытие или количество камней — та же модель с `confidence` не выше 0.8 и
описанием разницы; похожая, но другая модель (спиннер со Scroll против спиннера с
крестом) — не совпадение.

### Статусы

| Статус | Значение |
|---|---|
| `suggested` | пара найдена, ждёт оператора |
| `no_match` | ИИ не нашла совпадения среди кандидатов по названию |
| `no_match_swept` | прошли по фото весь каталог David — совпадения нет |
| `no_candidates` | детерминированный отбор не дал ни одного кандидата |
| `invalid_index` | ИИ вернула индекс вне списка — пару надо пересчитать |
| `error` | сбой вызова ИИ или разбора |
| `applied` | пара применена |
| `rejected` | оператор отклонил |

Повторный прогон берёт только `new`, `error` и `invalid_index`: «нет совпадения» и
отклонённое — это уже решения. Упавшие товары уходят в конец очереди, а не в
начало: иначе сбойный товар выбирается снова и снова, и очередь стоит на нём.

## Сплошной проход по фото

Кнопка **«По фото среди всех (N)»** лечит главный случай «ИИ не находит»: когда у
старого кольца нет модели в названии («Кольцо K&T», «Серебряное кольцо с
камнями», «Horseshoe», «Snake» — 14 колец из 146), отбирать по словам нечего, и
короткий список выходит пустым. Тогда модель смотрит фотографии:

1. **черновой проход** — по одной плитке на модель каталога, пачками по 27 плиток
   (три листа в запросе). Модель называет до пяти похожих;
2. **подробное сравнение** — только эти кандидаты, по три фото на модель.

Пачки нужны из-за размера запроса: один вызов на весь каталог (105 плиток,
12 листов) BYESU роняет с «system cpu overloaded». Сбой одной пачки не роняет
проход — остальные всё ещё могут дать пару.

В сравнение идут только фото с нашего S3. У импортированных колец это очищенные
кадры из карточки; у остальных — копии фото выгрузки, переехавшие на S3
(`supplier-media/david-studio/*`, см. [Зеркало фото поставщика](./david-studio-import.md#зеркало-фото-поставщика)).
Раньше кольца без карточки в Chromoff выпадали из подбора: их фото тянулись с
`cdn.shopify.com`, и недоступность CDN роняла весь запрос. Сколько колец ещё не
отзеркалено, показывает строка под статистикой (`candidatesSkipped`).

Пару с неимпортированным кольцом применить нельзя: переносить контент не из чего.
Экран скажет об этом прямо — сначала импортируйте карточку в David Studio.

## Ошибки провайдера

BYESU под нагрузкой отвечает `system cpu overloaded`, а сетевые обрывы дают
`Не удалось подключиться к BYESU`. Оба случая считаются временными: вызов
повторяется до пяти раз с ростом паузы (1 → 16 с), поэтому одна перегрузка
провайдера не превращается в статус `error`. Если провайдер лежит долго,
товар получает `error` и уходит в конец очереди — его подберут в следующий
прогон. Модель и провайдер берутся из «Выгрузок» → «Настройки ИИ».

**Выбирайте модель, которая видит изображения.** Через BYESU это
`claude-sonnet-4-6` и `claude-opus-4-8`; свежие `claude-*-5` отвечают «не вижу
изображения», и подбор вырождается в сравнение по названиям — пары находятся по
совпадению слов, а не по изделию (см. [Batch AI workflow](./batch-ai-workflow.md#какие-модели-claude-видят-изображения)).

### Материал обязателен

Правило промпта: жёлтое золото, белое золото, розовое золото и серебро — разные
позиции, даже когда модель одна. Материал карточки уходит в промпт отдельной
строкой (`jewelry_metal`, `metal_purity`), и при расхождении модель обязана
вернуть «совпадения нет». Поэтому «Кольцо Dagger с бриллиантами» из жёлтого
золота не сливается с серебряным Dagger от David.

## Прогон без браузера

Подбор можно запускать из терминала — теми же экшенами, что и кнопки:

```powershell
$env:SHARD='0'; $env:SHARDS='3'; $env:BATCH='3'
npx vitest run --config vitest.runner.config.ts     # подбор

$env:MIN_CONFIDENCE='0.9'
npx vitest run --config vitest.apply.config.ts      # применение найденных пар
```

Прогонщики (`__tests__/unit/lib/ring-match.runner.ts`, `ring-apply.runner.ts`)
подменяют админ-сессию и `revalidatePath`, поэтому работают без логина. `SHARDS`
делит 146 колец на независимые потоки: три процесса проходят каталог примерно за
15 минут вместо часа. Применение берёт пары с `confidence` не ниже
`MIN_CONFIDENCE`.

## Несколько старых карточек на одну модель David

В старом каталоге есть дубли: на одну модель David ссылаются две-три карточки
(например три «Серебряное кольцо с крестами» на один CH Plus Band). Первая пара
удаляет карточку дубля, поэтому следующая берёт контент из карточки-соседа, куда
он уже перенесён: фото David идут в ней первыми, их количество записано в отчёте
(`copied.photos`). Так все дубли получают контент David, а карточка дубля
удаляется один раз.

## Откат пары

Модель ошибается: в первом прогоне она разрешала «вариацию декора» и слила, например, широкое бандо David с тонким разомкнутым кольцом с паве-камнями. Поэтому у применённой пары есть откат (`revertRingMatchAction`):

1. старой карточке возвращается её название (оно сохранено в вердикте) и её
   собственные фото — фото David всегда идут первыми, поэтому достаточно отрезать
   первые `copied.photos` кадров;
2. заголовок и H1 листинга сбрасываются, чтобы витрина взяла восстановленное имя;
3. характеристики, пришедшие из карточки David (`sizes`, `measurements`,
   `model_name`, `jewelry_size`), удаляются;
4. описание пересобирается по СВОИМ фото кольца: прежний текст нигде не хранится,
   а текст David описывает другое изделие;
5. карточка David создаётся заново из черновика (`ai_output` в
   `david_import_drafts`), поэтому модель снова живёт отдельным товаром;
6. вердикт получает статус `reverted`.

Проверка применённых пар строгим промптом (`ring-recheck.runner.ts`) на 43 парах
дала 17 расхождений. Строгая проверка тоже не истина в последней инстанции: два
случая, разобранных глазами, оказались разными кольцами, а «с рельефным
орнаментом → Scroll Band» — одной моделью. Вывод: **автоматически применять пары
нельзя**, решение принимает человек; спорные пары (различие только в камнях)
остаются на ревью.

## Применение пары

`applyRingMatchAction` выполняет шаги:

1. **Перенос контента** (`buildRingMergePatch`): название, `h1`, описание и
   SEO-описание берутся у David; характеристики сливаются, значения David
   перекрывают старые; фото David идут первыми, старые остаются следом без дублей
   по `original_url`; карточка помечается `indexing_status: indexable`.
2. **Сброс SEO-полей листинга**: `seo_title`, `h1` и `seo_description` листинга
   очищаются. Без этого витрина продолжает показывать прежнее название: заголовок
   и H1 берутся из листинга и перекрывают товар. Пустые поля включают презентацию
   Rails — «Chrome Hearts <название из David> — <своя цена>».
3. **301** `/product/<slug дубля>` → `/product/<slug старого>` через
   `/admin/seo_redirects`, чтобы проиндексированный адрес не отдал 404.
4. **Удаление дубля**: сначала Chromoff-листинг, затем товар
   (`/admin/products/:id`, при отказе — `force_destroy`).
5. **Пометка черновика** David: `status='merged'`, ссылка на старую карточку в
   `merged_into_listing_id`, `rails_product_id` очищается. В выгрузке David такой
   товар получает метку «объединён со старым кольцом» и не выглядит созданным.

**Цена, варианты и статус старой карточки не меняются.** У David цена нулевая, а
смысл операции — сохранить живую карточку с ценой: у старых колец цены реальные
(например 45 000 ₽).

Если карточка David ещё не создана в Chromoff, применение останавливается с
понятной ошибкой: переносить нечего, сначала надо импортировать модель.

## Установка и проверка

```powershell
npm run db:migrate:david-ring-matches
```

Миграция создаёт `david_ring_matches` и добавляет в `david_import_drafts` колонки
`merged_into_listing_id`, `merged_into_product_id`, `merged_at`. Она же входит в
`npm run db:migrate:scraping`.

### Slug'и с повторами

Slug листинга собирается из бренда, названия и модели, поэтому модель, которая уже
есть в названии, попадает в адрес дважды:
`...-square-cemetery-...-square-cemetery-ring-ch-64538`. Такие адреса чистятся
дедупликацией слов; Rails при смене `legacy_slug` сам ставит 301 со старого адреса
на новый. Для колец это делалось по всему каталогу: 353 адреса с повторами, 270
исправлено, 15 отклонено Rails — их исправленный адрес уже занят историческим
редиректом (`Chromoff::SlugRedirector::Conflict`, наружу отдаётся 500).

Порядок проверки на живых данных:

1. «Выгрузки» → «Настройки ИИ»: выбран BYESU (Cockpit даст понятную ошибку).
2. Открыть `/admin/chromoff/david-rings`: в шапке видно число старых колец и
   моделей David; при недоступном Rails страница покажет текст ошибки.
3. «Подобрать 3» — три кольца получают вердикт; в журнале видно пары и сбои.
4. На уверенной паре сверить фото и нажать «Применить»: в карточке старого товара
   появляются фото David, название и характеристики; дубль исчезает из Chromoff,
   его URL отдаёт 301.
5. Убедиться, что цена старого товара не изменилась, а `indexing_status` стал
   `indexable`.

## Границы

- Применение пары необратимо: товар дубля удаляется. Первую пару стоит провести
  вручную и посмотреть результат на витрине.
- Экран намеренно не удаляет ничего сам: ИИ только предлагает пару.
- Витрина chromoff.store соблюдает `indexing_status` только после её выката;
  до этого дубли David продолжают индексироваться.
