# Импорт David Studio в Chromoff

Раздел: `/admin/chromoff/david-studio` — выгрузка поставщика, чистка фото от
вотермарки и импорт товаров в Chromoff.

Выгрузка поставщика лежит в `data/david-studio/catalog.json` (Shopify JSON,
456 товаров / 5386 фото) и обновляется командой:

```powershell
npm run catalog:sync:david-studio
```

Файл коммитится в репозиторий и обязан попадать в runtime-образ: в `Dockerfile`
каталог `data/` копируется в стадию runner отдельной строкой.

## Контур ИИ: модель из «Выгрузок», вызов с сервера

Черновик считает та же модель, что и остальной ИИ админки: провайдер, модель и
системный промпт берутся из «Выгрузок» → «Настройки ИИ» (сейчас это **BYESU**,
модель `gemini-3.8-flash-high`). Экшен собирает контактные листы фотографий и
вызывает провайдера с сервера:

```text
экшен → контактные листы из очищенных фото → BYESU (ключи прода)
      → сырой ответ → нормализация → david_import_drafts.ai_output
```

- Ключи BYESU живут в окружении сервера и привязаны к группе моделей:
  `BYESU_GEMINI_API_KEY` (Gemini Business), `BYESU_OPENAI_API_KEY` (OpenAI Codex) и
  `BYESU_CLAUDE_API_KEY` (Claude). На `/admin/ai-rules` видно, какие группы
  подключены: «Gemini ✓ · OpenAI — · Claude —». Группу выбирает имя модели:
  `gemini…` — Gemini, `claude…` — Claude, остальное — OpenAI Codex.
- Если Gemini недоступен, берите Claude: изображения через BYESU видят
  `claude-sonnet-4-6` и `claude-opus-4-8`, а свежие `claude-*-5` отвечают «не вижу
  изображения» (подробнее — в [Batch AI workflow](./batch-ai-workflow.md#какие-модели-claude-видят-изображения)).
- Провайдер **Cockpit** доступен только с локального воркера, поэтому при нём
  экшен возвращает понятную ошибку, а не таймаут: выберите BYESU или OpenRouter.
- Ошибки модели и разбора ответа видны в интерфейсе: блок «Черновик ИИ» с
  текстом ошибки и кнопкой «Повторить расчёт».
- Нормализация и фильтрация характеристик выполняются на сервере, поэтому
  воркеру не нужно ничего знать про реестр и Rails.
- Вызов долгий: 9 фото = 1 контактный лист ≈ 60 с. Это серверный экшен, поэтому
  у прокси перед приложением должен быть запас по таймауту.

## Поля черновика

| Поле | Кто заполняет |
|---|---|
| Название, описание, альты | модель |
| Категория и подкатегория каталога | модель; в ревью это проверяемые поля |
| Категория Chromoff | модель; пустой id или уверенность ниже 0.75 → `needs_review` |
| Характеристики (`catalog_attributes`) | модель, только коды схемы выбранной категории |
| Размеры и замеры | сервер, из вариантов поставщика |
| Цена | всегда 0 |

### Характеристики по схеме категории

Реестр характеристик уходит в промпт картой «область категории → коды», поэтому
модель берёт группу своей категории и общие коды. После ответа сервер повторно
фильтрует характеристики по выбранной категории
(`filterCatalogAttributeDefinitionsForCategory`), так что код из чужой категории
до товара не доходит.

### Размеры и замеры из вариантов

Варианты David — одна ось с разным содержимым: `6.3 IN / 16 CM（Suitable For
Wrists 14CM）`, `Waist Circumference 28IN（Belt Length 84CM）`, `US4.5`,
буквенные размеры, а также цвета и служебные подписи (`Choose an option`,
`Per Piece`, `Pendant Only`).

Правила разбора (`lib/david-studio-sizes.ts`):

- сантиметры поставщика — источник истины, дюймы переводятся (2.54), диапазоны
  сохраняются (`14-17 CM` → `14–17 см`);
- US-размеры колец остаются как есть: таблицу US→мм мы не подставляем и диаметр
  не выдумываем;
- цвета и служебные подписи размером не считаются;
- в таблицу замеров идёт одна строка на размер: `16 см` + пояснение
  `подходит для запястья 14 см` в колонке «Посадка»;
- `catalog_attributes.sizes` заполняется этими же значениями, из них Rails
  создаёт варианты.

### Цена 0

Цена у товара и у всех вариантов — 0. Rails считает `price_on_request = true`
при нулевой цене, поэтому витрина показывает «Цена по запросу» и не даёт
оформить заказ. Товар при этом публикуется (`status: active`), а
`indexing_status: noindex` оставляет карточку вне поиска основного магазина:
товары David продаются на Chromoff. Витрина chromoff.store соблюдает этот статус
(sitemap и meta robots), поэтому карточки с ценой по запросу не индексируются.
Цена поставщика в USD остаётся в интерфейсе справочной строкой.

## Массовая чистка фото

В выгрузке у каждого товара есть чекбокс, кнопка «Очистить фото выбранных» и
счётчик «выбрать все на странице». Задания на чистку кладутся в
`photo_clean_jobs`, чистку выполняет локальный воркер LaMa:

```powershell
node scripts/photo-clean-worker.mjs        # один воркер, не несколько
```

Прогресс по каждому товару виден в выгрузке (`очищено 12/19`, «фото очищены»),
страница обновляется сама, пока в очереди есть задания.

Кнопка **«Очередь фото»** открывает модалку с остатком работы: всего кадров,
сколько осталось, в работе, очищено, на глаза, не найдена, ошибки — и список
товаров, где ещё есть незабранные кадры, со ссылкой на карточку. Данные берутся
из `GET /api/david-photo-queue` и обновляются сами, пока очередь не разобрана.

Метки товара в выгрузке:

- **опубликован в Chromoff** — у черновика есть созданный товар (`rails_product_id`);
- **объединён со старым кольцом** — карточка влита в старое кольцо и удалена
  (см. [Развязка дублей колец](./david-ring-matches.md));
- **фото очищены** — все фото товара обработаны без сбоев;
- **черновик готов / ИИ: ошибка** — состояние черновика.

### Фильтр по состоянию импорта

В сайдбаре выгрузки есть фильтр **«Состояние»** со счётчиками по текущему разделу:

| Значение | Когда показывается |
|---|---|
| Необработанное | очищены не все кадры (в том числе когда чистку не запускали) |
| Обработанное | все кадры очищены, товар в Chromoff ещё не создан |
| Опубликованное | товар создан в Chromoff |

Состояния взаимоисключающие: опубликованное важнее обработанного, поэтому один
товар не попадает в две вкладки. Статусы читаются из `photo_clean_jobs` и
`david_import_drafts` по всему каталогу, а не по текущей странице: иначе фильтр
считал бы остаток неверно.

## Просмотр и удаление кадров в товаре

На экране товара очищенные кадры показаны парами «до / после», а рядом — сколько
кадров осталось в импорте и сколько убрано. Главные действия (**сделать черновик
ИИ**, **создать товар** / **присоединить к существующему**) закреплены в нижней
панели экрана и остаются на виду при прокрутке длинной формы.

- клик по кадру открывает его в полном размере: очищенный из S3 или оригинал
  поставщика, плюс ссылки на кропы «до» и «после»;
- кнопка с корзиной убирает кадр из импорта;
- убранные кадры не пропадают: они перечислены в блоке «Убрано из импорта» и
  возвращаются кнопкой «вернуть», в том числе прямо из модалки просмотра.

Альты фотографий править не нужно: их делает ИИ и они подставляются в товар
автоматически — в интерфейсе ревью поля альтов нет.

При привязке к существующему товару список найденных товаров показывает превью
каждого — видно, к какой карточке присоединяются фото.

Кнопка «назад» на экране товара возвращает к выгрузке **с теми же фильтрами**:
каталог передаёт текущий запрос параметром `from`, а экран товара возвращает его
в адрес выгрузки (в том числе из модалки очереди).

Удаление — это исключение, а не потеря результата: файл в S3 и задание чистки
остаются на месте, кадр перестаёт попадать в промпт ИИ, в создаваемый товар и в
привязку к существующему товару. Хранится в `david_photo_exclusions` (миграция
`npm run db:migrate:david-photo-exclusions`, она же в `db:migrate:scraping` и в
`CMD` контейнера).

### Повторная чистка проблемных кадров

Обычная постановка заданий повторно их не берёт (`ON CONFLICT (source_key) DO
NOTHING`), поэтому у кадров «не найдена», «на глаза» и со сбоем есть отдельная
кнопка **«Переочистить проблемные (N)»** — в карточке товара и в модалке очереди
(там она без указания товара, то есть по всей выгрузке).

- перезапуск переводит кадр в `pending` и очищает метрики, но **не** стирает
  файлы в S3: пока воркер обрабатывает кадр заново, в карточке видны прежние
  кропы «до/после»;
- кадры со статусом `ok` не трогаются;
- нужно это после улучшений детектора: раньше такие кадры приходилось возвращать
  в очередь вручную через SQL.

### Ручная пометка вотермарки

Если вотермарка на кадре есть, а детектор её не нашёл (светлое по светлому,
тёмный фон, надпись поверх металла), оператор обводит её сам:

1. на экране товара открыть кадр в полном размере;
2. нажать **«Отметить вотермарку»** и обвести надпись мышью;
3. нажать **«Очистить по рамке вне очереди»**.

Что происходит:

- кадр получает `priority = 10` и снова становится `pending`, поэтому воркер
  берёт его **раньше остальной очереди** (обычные задания имеют приоритет 0);
- чистка идёт **ровно по нарисованной рамке**: детектор не участвует, статус
  `miss` для такого кадра невозможен — он либо `ok`, либо `review`;
- рамка сохраняется в `photo_clean_jobs.manual_box`, поэтому повторный запуск
  кадра («переочистить проблемные») снова использует её, а кнопка «Снять
  пометку» возвращает кадр в автоопределение;
- **рамка затирается целиком** силами LaMa: обводите только саму надпись и не
  захватывайте изделие — всё, что попало в рамку, будет перерисовано. Результат
  сразу виден в кропах «до/после», а кадр можно вернуть в автоопределение или
  убрать из импорта.

Колонки `priority` и `manual_box` добавляет миграция
`npm run db:migrate:photo-clean-manual-box` (она же в `db:migrate:scraping` и в
`CMD` контейнера).

## Привязка к существующему товару

Вкладка «К существующему товару» ищет товар в опубликованных Chromoff-листингах
и дописывает к нему фото, характеристики и замеры.

- Фото, которые уже есть у товара, пропускаются по `original_url`.
- Характеристика пишется только если у товара её ещё нет: существующие значения
  сохраняются и перечисляются в отчёте («не перетирая то, что там есть»).
- Название, описание и категории существующего товара не меняются.
- Два явных переключателя снимают неоднозначность:
  - «обнулить цену товара и вариантов» — правило цены David. Для товаров с
    `external_id`, начинающимся на `david-studio-`, включается автоматически;
  - «сделать товар активным» — скрытый товар не виден и в Chromoff. Для товаров
    этого импорта включается автоматически.
- Вариант без размера и без SKU Rails не даёт обновить через payload товара:
  у такого варианта сохраняется прежняя цена. На витрине это безопасно, потому
  что нулевая цена товара включает «Цена по запросу».

## Зеркало фото поставщика

Фото в выгрузке лежат на `cdn.shopify.com` — чужом CDN. Он бывает недоступен, и
тогда падает целый запрос: например, сравнение колец обрывалось на скачивании
контактного листа. Поэтому фото переезжают на наш S3:

```powershell
npm run media:mirror:david-studio                      # кольца, все фото
node scripts/mirror-david-studio-media.mjs --scope all # весь каталог (456 товаров, ~2.9 ГБ)
node scripts/mirror-david-studio-media.mjs --dry-run   # только посчитать
```

- Ключ строится по содержимому: `supplier-media/david-studio/<sha256>.<ext>`.
  Одинаковые кадры разных товаров занимают одно место, а адрес не зависит от
  порядка выгрузки.
- Соответствие «адрес поставщика → наш адрес» хранится в `david_media_mirror`
  (миграция `npm run db:migrate:david-media-mirror`, она же в `db:migrate:scraping`
  и в `CMD` контейнера). Повторный запуск пропускает уже зеркалированное, поэтому
  скрипт можно прерывать и догонять.
- У адреса поставщика отбрасывается query-строка: у Shopify там версия файла,
  и без этого один кадр попал бы в зеркало дважды.
- Объём: кольца — 1534 фото (~800 МБ), весь каталог — 5386 фото (~2.9 ГБ).

Зеркало — это рабочая копия фото поставщика, а не замена чистке: в витрину
по-прежнему уходят только очищенные кадры из `products/media/*`.

## Проверка

1. В «Выгрузках» → «Настройки ИИ» выбран провайдер BYESU (или OpenRouter) и модель.
2. На экране товара есть очищенные фото; кнопка «Сделать черновик ИИ» считает
   черновик и показывает, какой провайдер и модель ответили.
3. Ошибка модели (недоступный ключ, пустой ответ, выбран Cockpit) видна текстом
   в блоке «Черновик ИИ» и повторяется кнопкой «Повторить расчёт».
4. Создание товара: цена 0, размеры из вариантов, замеры одной строкой на размер.
5. Привязка к существующему товару: повторный запуск не дублирует фото и не
   перетирает заполненные характеристики.
