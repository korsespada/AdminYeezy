# AI-обработка китайских товаров в «Выгрузках»

Раздел `/admin/batches` — единый production-конвейер китайских товаров. Экспериментальный `/admin/exports-v2` удалён вместе с таблицами `scraping_v2_*`.

## Этапы

Каждая выгрузка проходит четыре отображаемых этапа:

1. `Сырой товар` — результат парсера поставщика с китайским текстом и всеми фотографиями.
2. `Обработан скриптом` — поставщик-специфичный Python-скрипт удалил служебные карточки, объединил альбомы, переставил фотографии или заполнил известные поля.
3. `Обработано ИИ` — мультимодальная нормализация карточек и SEO.
4. `Запушено в БД` — отдельная ручная публикация в Rails-каталог.

После сырого импорта, скрипта и AI сохраняется снимок товаров. Действие «Откатить к этапу» восстанавливает выбранный снимок и удаляет более поздние снимки и AI-запуски. Оно нужно, если результат скрипта или AI не подходит; обычное редактирование отдельного товара отката не требует.

## Провайдеры AI

В `/admin/ai-rules` можно добавить сторонний OpenAI-compatible или Anthropic-compatible провайдер: название, Base URL и API-ключ; модель указывается только если endpoint не предоставляет `/models`. Отдельного поля «Тип» нет: протокол определяется автоматически по домену и URL. OpenRouter, BYESU и обычные совместимые сервисы используют `/chat/completions`; Anthropic и AgentRouter используют Messages API `/messages`, а для AgentRouter добавляется требуемый beta-маршрут. Base URL можно указывать без конечного endpoint (например, `https://openrouter.ai/api/v1` или `https://agentrouter.org/v1`). После добавления AdminYeezy пытается получить `/models`; список можно обновить кнопкой рядом с провайдером. Для сохранённого провайдера доступны проверка подключения и редактирование; при редактировании пустой API-ключ сохраняет прежний ключ. API-ключ хранится в `ai_providers.api_key_ciphertext` с AES-256-GCM и не возвращается в браузер.

Для шифрования требуется секрет окружения `AI_PROVIDER_ENCRYPTION_KEY`. Если сохранённый провайдер не выбран, сохраняется прежняя совместимость с `OPENROUTER_API_KEY` и `BYESU_*_API_KEY`. Удаление провайдера очищает его выбор; уже запущенные AI-задачи продолжают использовать snapshot без хранения открытого ключа.

## Кастомные скрипты поставщиков

Основное хранилище этапов — `products` и JSONB-таблица `batch_snapshots`.

1. `SzwegoParser.py` возвращает массив товаров в JSON.
2. При импорте каждому товару присваивается неизменяемая исходная позиция `source_position`.
3. Python post-process получает JSON через stdin и возвращает JSON через stdout.
4. Результат сохраняется в `products`, партия получает этап `SCRIPT_PROCESSED` и JSONB-снимок.

Порядок особенно важен для скриптов, объединяющих соседние альбомы. CSV автоматически не создаётся и остаётся только ручным форматом экспорта. Старые скрипты подключены к единому runner; новые скрипты должны реализовывать `process_products(products)`.

Для поставщика `CH Одежда` (`_Z4krSCEyDqn5hvTYMJDEp4rykS4WwC0I`) используется `process_ch_clothing_timeline.py` вместе с источником `Единая лента`. Скрипт считает длинную товарную карточку точкой завершения блока: добавляет к ней предшествующие альбомы с `局部细节`, фурнитурой/вышивкой и видео из `实拍视频`, а таблицы размеров, фото на моделях, отдельные карточки упаковки и подборки образов исключает. Дополнительно исключаются подписи с символом `‼️`, отдельные объявления о наличии/отправке, контроль качества, производство, демонстрация ткани/цвета, витрина и типовые фото на моделях. Упоминание упаковки, 925-фурнитуры, `热固油材质印花` или `现货秒发` внутри развёрнутого описания самой CH-карточки не отбрасывает товар. Несколько видео сохраняют порядок и назначаются следующим карточкам по очереди. `➨` очищает незавершённый блок, но не является единственным разделителем — поставщик публикует соседние товары и без него. Соседние альбомы без разделителя объединяются только если у длинного (от 8 фото) и короткого (до 6 фото) альбомов общий китайский фрагмент названия; обычные цветовые карточки не склеиваются. В редакторе карточки можно вручную заменить ссылку видео и, необязательно, его постер; ручная ссылка имеет приоритет и будет перенесена при публикации. В сетке партии технические `attributes` скрыты, но остаются доступны в редакторе карточки.

Для `Chanel Сумки` (`_dmTrSFHqEWfdIw-LMbwscczrR7MF5hAU6p_QQHQ`) `process_chanel_bags_timeline.py` читает единую ленту как блок «упаковка → видео → основной альбом → детали», но выводит галерею как «основной альбом → детали → упаковка». Если сначала опубликован технический альбом с крупными планами, а следующий совпадающий альбом содержит содержательное описание товара, второй альбом становится главным и переносится в начало галереи. К одному основному альбому присоединяется только первый следующий короткий альбом деталей: последующие короткие карточки с тем же ярлыком считаются lookbook/фотосессией на другом фоне и исключаются, а не становятся самостоятельным товаром. При включённом `Парсинг тегов` исходный ярлык сохраняется в `attributes.szwego_tags` и является обязательным ключом склейки; старые снимки без него склеиваются только при точном совпадении артикула. Общая китайская рекламная фраза никогда не является доказательством одного товара. Поэтому аксессуар без деталей остаётся самостоятельным товаром с основной галереей, упаковкой и видео. Описание упаковки исключается, а ссылка видео сохраняется в `attributes.szwego_video_url`. Коллажи/сравнения и посты `合集`, `ZP`, первой/финальной версии, качества или разработки не становятся товарами. Совпадающие URL фото удаляются мгновенно; URL-разные визуальные дубли остаются для AI-очистки галереи и не задерживают постобработку.

## Папки

Папка создаётся вручную и объединяет независимые выгрузки разных поставщиков. Поставщики не запускаются группой. Выгрузку можно перемещать между папками или вернуть в «Без папки». Удаление папки не удаляет выгрузки.

## Изображения

Фото включаются отдельно у каждого поставщика. Если настройка выключена, AI получает только исходный текст и не распознаёт визуальные таблицы размеров. Если включена, изображения отправляются contact sheet по девять кадров, сеткой 3×3; для длинной галереи создаётся несколько листов. Нумерация сквозная.

Опциональное «Уточнение по оригиналу» разрешает второй vision-запрос только при низкой уверенности: AI выбирает до трёх кадров с плохо читаемым логотипом, брендом или моделью и получает их в исходном размере.

При обычной AI-обработке, если у поставщика включены фотографии, alt создаются в том же первом vision-проходе, что и карточка товара. Второй vision-запрос для alt не выполняется. Если обработка фотографий у поставщика выключена, alt заполняется названием товара. Для уже опубликованной **самой последней** выгрузки доступен отдельный запуск `Сгенерировать alt + slug`: перед запуском AdminYeezy получает из Rails финальный slug товара с внутренним SEO-артикулом. Затем AI получает contact sheet 3×3 и возвращает только alt, не запрашивая каждую фотографию отдельно. Slug фото сервер строит транслитерацией соответствующего alt, сокращая его до 120 символов и добавляя номер только при совпадении. Уточнение по оригиналам в этом режиме отключено. Slug товара строится как `бренд-название-модель-цвет-внутренний-артикул` в латинице; `external_id` в него не входит. Alt всегда содержит подтверждённый бренд, пишется по-русски с целевой длиной 60–120 символов и жёстким максимумом 160. Alt виден в браузерной подсказке при наведении на фото в карточке товара.

AI может:

- исключить рекламу, дубли и нерелевантные кадры из публичной галереи. Фото с основным товаром рядом с упаковкой или другим товаром сохраняется, если основной товар хорошо виден и остаётся главным объектом; исключаются только кадры, где посторонний объект доминирует или делает товар неясным. Крупный наложенный промо-/информационный текст, цена или призыв на любом языке исключает кадр, а небольшой логотип или водяной знак — нет;
- определить таблицу размеров, извлечь размеры и не публиковать саму таблицу;
- сопоставить признаки на фото с китайским текстом.

Исходный текст считается ненадёжным: он может относиться к соседней карточке или другой модели. При включённых фотографиях AI сначала определяет согласованный товар по всей серии кадров, а затем проверяет текст. Если источники прямо противоречат друг другу, модель, тип товара, цвет, материал, фурнитура, классификация и публичные тексты строятся по фотографиям; противоречащая часть текста отбрасывается. Если фото лишь не позволяет рассмотреть материал или деталь, это не считается противоречием: явно указанный технический факт сохраняется. До трёх оригиналов разрешено запросить не только при низкой общей уверенности, но и для разрешения конфликта текста и изображений.

Исходные фотографии остаются в снимке этапа и восстанавливаются откатом.

## Результат AI

В технической БД до публикации сохраняются:

- `name`, `description`, `h1`, `seo_title`, `seo_description`;
- существующие ID бренда, категории и подкатегории;
- пол и структурированные `attributes`;
- уверенность, ошибка отдельного товара и предложение цветового семейства.

Для последней выгрузки отдельный режим `Сгенерировать alt + slug` перезаписывает в технической БД `slug`, `photo_alts` и `photo_slugs`. Он не меняет название, описание, цену, классификацию, атрибуты и публичную галерею до отдельной публикации. AI не создаёт новые бренды или верхнеуровневые категории.

## Тест и повторная обработка

Первый запуск обрабатывает первые 10 товаров в исходном порядке и сразу записывает результат отдельным блоком проверки. До запуска сохраняется снимок. Кнопка «Продолжить ИИ» обрабатывает остальные товары с тем же snapshot провайдера, модели, промпта, temperature и max tokens, даже если глобальные настройки изменились.

Ошибки одного товара не останавливают остальные. Ошибочный или уже обработанный товар можно запустить повторно; перед повтором также создаётся снимок.

Для партии со статусом `Запушено в БД` доступна кнопка `Переобработать ИИ`. Она создаёт снимок опубликованного состояния, помечает выбранные товары ожидающими AI, применяет текущие настройки, промпт и справочники и переводит успешно завершённую партию обратно в `Обработано ИИ`. Существующая цена и `price_source` сохраняются. После проверки результат публикуется режимом `Обновить и добавить`, поэтому Rails-товары с тем же `external_id` обновляются без создания дублей. Можно переобработать всю партию или только выбранные после фильтрации.

Действие `Восстановить таблицы замеров` не переобрабатывает карточки и не снимает с партии статус `Запушено в БД`. Оно объединяет сохранённые скриптовые связи одежды и обуви с исходными фотографиями таблиц, распознаёт каждую уникальную таблицу один раз и записывает `attributes.measurements` и размеры строк в `attributes.sizes` в связанные товары, где замеров ещё нет. Названия, описания, цены, классификация, цвета и публичные галереи при этом не меняются.

При обновлении ранее опубликованной партии фотографии, уже находящиеся в S3 или прикреплённые к существующему Rails-товару с тем же `external_id`, используются повторно. После `Сгенерировать alt + slug` ближайшее действие `Обновить каталог` один раз перевыкладывает фото последней партии в WebP под именами `{slug-товара}-{slug-фото}.webp`, передаёт в Rails slug и alt каждого изображения, а после успешной публикации удаляет устаревшие файлы только из S3-префикса этой партии. Успешно применённый SEO-запуск помечается опубликованным и не вызывает повторное перекодирование или удаление при следующих обычных пушах. Если у старой партии сохранились исходные внешние URL, а доступ к бакету не настроен, режим `Обновить и добавить` сохраняет текущую Rails-галерею и обновляет остальные поля. `S3_BUCKET` требуется только для переноса действительно новых внешних фотографий.

Общий системный промпт не содержит классификацию всех возможных категорий. Отдельные наборы из реестра `Автоматические правила категорий` подключаются к запросу только при совпадении категории конкретного товара и имеют приоритет над инструкцией поставщика. Текущие наборы для `Сумки` и `Обувь` можно просмотреть на странице `Настройки ИИ`; остальные категории добавляются по мере появления подтверждённых сценариев.

### Повторный поиск цветовых вариантов

После полной AI-обработки рядом с кнопкой публикации доступна кнопка `Найти варианты`. Это отдельный AI-запуск с режимом `variants`, а не повторная SEO-обработка.

- Проверяются только товары с `ai_processed=true`, которым ещё не назначен `variant_group_key`.
- В модель передаются название, описание, бренд, категория, подкатегория, пол и уже сохранённые атрибуты. Фотографии, contact sheet, оригиналы и визуальные эталоны цен не передаются.
- Используются текущие глобальные провайдер и модель из `/admin/ai-rules`.
- AI возвращает только `color_family` или `null`. Название, SEO, цена, классификация, атрибуты и галерея товара не изменяются.
- Для сумок должны совпасть бренд, точная модель, габариты в том же порядке измерений, материал и фурнитура; для обуви — бренд, модель, конструкция и материал; для одежды — бренд, модель/фасон и материал. Цвет исключается из сигнатуры. Например, `30 × 26 × 14` и `26 × 30 × 14` считаются разными размерами.
- Сервер объединяет одинаковые сигнатуры и показывает предложение только при наличии минимум двух товаров и двух различных цветов.
- Если у поставщика включено `Проверять подряд идущие товары как цветовое семейство`, после успешной полной AI-обработки автоматически запускается поиск непрерывных групп из 2–8 обработанных карточек с одинаковыми брендом и категорией. Это запасной путь для поставщиков без надёжных артикулов: AI получает первые фото и метаданные соседних карточек, сравнивает фасон, принт, конструкцию и материал и возвращает только уверенные семейства. Разные модели в одной последовательности он обязан пропустить. Найденные семьи всегда остаются предложениями до ручного одобрения. Кнопка `Найти варианты` остаётся ручным повторным запуском.
- Поиск семейства не переносит и не объединяет фотографии: каждая карточка хранит только свою галерею и, при наличии, своё видео.

### Разделение одного альбома на цветовые товары

В карточке товара с двумя и более фотографиями доступна кнопка `Разделить по цветам`. Она делает один vision-запрос: AI распределяет фотографии отдельных экземпляров по цветам и в том же JSON полностью заполняет название, описание, SEO, классификацию, атрибуты, цену и alt каждого нового товара. Второй AI-проход для созданных карточек не выполняется.

Сервер проверяет, что получено от 2 до 8 уникальных цветов, одна фотография не назначена нескольким товарам и у каждого варианта есть фотография. Затем одной транзакцией исходный товар превращается в первый цвет, остальные создаются с детерминированными `external_id`, все сразу получают `ai_processed=true` и общий стабильный `variant_group_key`. Общие кадры с несколькими цветами можно не включать ни в один вариант. Если у исходного видео есть poster, он отправляется AI отдельным ненумерованным кадром: AI выбирает один из уже найденных `color_key`, и видео сохраняется у соответствующего варианта. Если цвет неясен или в превью несколько цветов, видео остаётся у первого варианта; оно никогда не копируется во все карточки. Режим доступен для BYESU и OpenRouter; Cockpit worker эту специальную схему пока не обрабатывает.
- Процесс можно остановить. Уже найденные предложения сохраняются.

### Постоянные настройки AI поставщика

В настройках поставщика (`Настройки AI поставщика` в меню выгрузки или `/admin/suppliers`) есть постоянный блок правил AI-обработки. Эти параметры не запускают отдельный постпроцесс: они сохраняются у поставщика и автоматически применяются к `Тесту 10 товаров` и `Полной обработке` всех его выгрузок.

- `Группировать по артикулу` принимает пример вроде `SP001 blue`; AI отделяет цвет от общей основы и формирует цветовую семью.
- `Проверять подряд идущие товары как цветовое семейство` после полной AI-обработки автоматически добавляет соседние карточки как кандидатов, даже когда артикул отсутствует или названия цветов различаются. Эта настройка не объединяет галереи; `Найти варианты` остаётся ручным повторным запуском.
- `Разделять разные цвета внутри одного альбома` выполняет разделение и полную обработку вариантов одним запросом. Если цветов нет, сохраняется одна обычная карточка.
- `Поставить лучший кадр первым` меняет только первое фото, остальные и их alt сохраняются в порядке.
- `Исключать альбом только с фото моделей` удаляет товар из текущей версии, но исходная карточка остаётся в снимке для отката.

Провайдер, модель, промпт и фактические параметры обработки записываются в `batch_ai_runs.settings_snapshot`, поэтому каждый запуск воспроизводим. При продолжении полной обработки используются актуальные постоянные правила поставщика.

### Видео поставщика

Парсер Szwego сохраняет обычные фотографии отдельно от ссылки видео, даже если API возвращает медиа вложенным объектом. Поддерживаются `videoUrl`/`videoURL`, вложенные `pvod/*.mp4` и poster/cover URL. В карточке выгрузки видео показывается отдельным плеером с poster и стандартными кнопками управления. При публикации `scripts/batch-workflow.js` сжимает исходник через FFmpeg в MP4 H.264/AAC, генерирует poster WebP и сохраняет оба объекта в S3; в Rails передаются `video_url` и `video_poster_url`.

После завершения автоматически открывается окно `Предложения ИИ`. Утверждение предложения назначает затронутым товарам общий `variant_group_key`; отклонение не меняет товары.

## Провайдеры

Глобальная настройка на `/admin/ai-rules` выбирает `OpenRouter` или `Cockpit`. Эта страница является единственным интерфейсом глобальных batch AI-настроек; раздел выгрузок использует сохранённые значения.

- OpenRouter вызывается сервером AdminYeezy; модель задаётся в интерфейсе.
- Cockpit обрабатывает очередь локальным `scripts/batch-ai-worker.js`; модель задаётся `COCKPIT_MODEL` на worker. Команда `ai:catalog-worker` запускает вместе SEO worker и batch worker.
- Системный и пользовательский промпты одинаковы для провайдеров.
- Если Cockpit heartbeat старше 30 секунд, новый запуск сразу отклоняется.

Запуск обоих worker:

```bash
npm run ai:catalog-worker
```

Для отдельного запуска только batch-очереди остаётся `npm run ai:batch-worker`. Обязательные env: `BATCH_AI_WORKER_TOKEN` (либо `AI_CATALOG_WORKER_TOKEN`), `COCKPIT_API_URL`, `COCKPIT_API_KEY`. `ADMINYEEZY_URL` обязателен вне локальной машины; локально используется `http://localhost:3000`. Количество одновременных запросов задаётся на `/admin/ai-rules` и передаётся worker через heartbeat.

## Промпты

Итоговый контекст состоит из общего системного промпта, необязательной инструкции поставщика, справочников Rails, схемы атрибутов, исходного товара и, если разрешено, contact sheet. Инструкция поставщика хранит только особенности его ленты; полный отдельный промпт не требуется.

У поставщика категории, подкатегории и бренды задаются необязательными множественными ограничениями. Пустой список разрешает AI выбирать по всему справочнику. Непустой список ограничивает выбор указанными значениями, но не назначает первый вариант принудительно. Ограниченные подкатегории дополнительно фильтруются по родительской категории. Если поставщик разрешает только одну категорию, AI получает только её подкатегории. При нескольких допустимых категориях передаётся общий разрешённый список с `parent_id`, чтобы AI мог исправить ошибочную исходную категорию, а сервер проверяет соответствие подкатегории итоговой категории.

Глобальные правила каталога применяются поверх инструкций любого поставщика. Для категории `Сумки` итоговая техническая подкатегория `Сумки` запрещена: AI обязан выбрать конкретную существующую подкатегорию. `Сумки-косметички`, `Сумки-кейсы`, `Сумки с клапаном`, `Сумки-багет`, `Мини-сумки`, `Сумки-боулинг` и `Пляжные сумки` не создаются и не назначаются; такие результаты сервер автоматически переводит в `Сумки на плечо`. `Сумки-хобо` и `Сумки-тоут` сохраняются отдельными подкатегориями как устойчивые типы конструкции. Если AI всё равно возвращает общую подкатегорию `Сумки`, товар завершается с ошибкой и требует повторной обработки. `Caviar`, кавьяровая и зернистая кожа считаются фактурой и нормализуются в материал `Кожа`; подтверждённые `Кожа ягнёнка` и `Телячья кожа` сохраняются отдельными материалами.

Для всех поставщиков категории `Обувь` используется закрытый справочник конструкций и правила из [shoe-taxonomy.md](./shoe-taxonomy.md). Фотографии определяют тип обуви, а текст подтверждает размеры и материалы. AI не создаёт новые обувные подкатегории; известные синонимы вроде `Дерби`, `Сабо` или `Босоножки` автоматически сводятся к существующим группам.

Гендер обуви определяется AI по совокупности явного текста, полного размерного ряда, атрибутов и фотографий. Явное указание и `audience` у группы размеров имеют приоритет; размерный ряд используется как признак, а не как безусловный порог. Женские размеры могут доходить до 41, мужские часто начинаются с 39, а спорные ряды вроде `38–45`, `38–41` и `36–44` AI решает по контексту и фото либо возвращает пустое значение при недостаточной уверенности. Половинки сохраняются только при явном указании; из обычного `36–45` половинки не добавляются. Эта логика общая для категории, а не настройка конкретного поставщика.

Для категории `Одежда` также используется только существующий справочник подкатегорий. Известные названия и синонимы нормализуются сервером, а неизвестный результат не создаёт предложение новой подкатегории: товар сохраняется без подкатегории и требует ручного выбора или повторной обработки после обновления справочника.

В открытой выгрузке можно выбрать произвольные товары и запустить для них отдельную AI-обработку через массовую панель. Такой запуск не меняет статус всей партии. Во время выполнения над фильтрами показываются прогресс и ближайшие товары очереди с фотографиями. Фильтры по модели и цвету строятся по уже записанным атрибутам и включают варианты `Без модели` и `Без цвета`.

Поля `brand`, `category` и `subcategory` внутри технической партии хранят канонические Rails UUID, но интерфейс всегда показывает их названия. При открытии старого снимка локальная таблица `catalog_id_mappings` используется как резервный источник подписей. Инструкции поставщика перед отправкой в AI автоматически очищаются от старых PocketBase ID и устаревших требований к формату ответа; справочники из текущего запуска всегда имеют приоритет.

Облачный AI можно запускать через OpenRouter или OpenAI-совместимый BYESU API, локальную обработку — через Cockpit. BYESU привязывает API-ключ к группе моделей, поэтому в server environment используются отдельные глобальные секреты: `BYESU_GEMINI_API_KEY` для группы Gemini Business и `BYESU_OPENAI_API_KEY` для группы OpenAI Codex. AdminYeezy автоматически выбирает ключ по модели: `gemini-3.1-flash-lite` использует Gemini Business, `gpt-5.6-luna` — OpenAI Codex. Ключи не хранятся в настройках поставщика. Старый `BYESU_API_KEY` поддерживается как временный fallback; его группу задаёт `BYESU_API_GROUP=gemini|openai` (по умолчанию `openai`). Как и остальные настройки, провайдер и модель фиксируются snapshot-ом конкретного запуска.

SEO AI Studio (`/admin/seo-ai`) использует BYESU по умолчанию для всех задач. Для `catalog_product_enricher` модель по умолчанию — `gemini-3.1-flash-lite`. В настройках можно явно выбрать BYESU, OpenRouter или Cockpit; выбор сохраняется в Rails и попадает в snapshot каждой генерации. Для одежды действуют глобальные правила классификации: AI выбирает только существующую подкатегорию, не создаёт новые подкатегории, а устаревшую «Кофты» распределяет по точному типу товара — например, футболки/поло и вязаные футболки с коротким рукавом в «Футболки и майки», короткая планка с несколькими пуговицами считается поло, а застёжка на пуговицы по всей передней части — рубашка.

## Цены

AI не придумывает цену. В карточке поставщика доступны условные правила по бренду, категории, подкатегории, модели, материалу, `size_class` (`small`, `medium`, `large`) и диапазонам ширины/высоты сумки. К правилу можно приложить до 9 фотографий и текстовую подсказку. Текстовые условия всех правил передаются AI, а визуальные эталоны предварительно отбрасываются только для правил, которым уже известные поля товара явно противоречат; подходящие эталоны передаются отдельным contact sheet и не смешиваются с фотографиями товара.

AI определяет `model_name`, `bag_width_cm`, `bag_height_cm`, `size_class` и, при уверенном визуальном совпадении, `price_rule_key`. Сервер назначает цену детерминированно: точный визуальный эталон важнее правила модели и размеров, а они важнее резервного правила размерного класса. Количество фотографий в альбоме никогда не используется как условие цены.

В правилах поставщика можно выбрать `Кастомная формула AI`. В поле инструкции описывается, что искать в исходном тексте, например: «возьми максимальную цену из диапазона, умножь на 13 и 2.5». AI выбирает `price_rule_key`, а сервер извлекает суммы рядом с валютой/ценовым маркером, применяет `source_price` (`max` или `min`), множители и округление (`nearest`, `up`, `down`). Для `💰2399—4599`, множителей `13` и `2.5` и шага `1000` результатом будет `149000` при обычном округлении или `150000` при округлении вверх. Если цена в исходнике не найдена, кастомное правило не подставляет ноль и используется стандартная цена поставщика.

Приоритет:

1. ручная цена;
2. наиболее конкретное правило, затем больший числовой приоритет;
3. цена постпроцессора, если конкретный поставщик всё ещё её задаёт;
4. стандартная цена поставщика;
5. `0`.

При сохранении и перед каждым применением правила его условия `brand`, `category` и `subcategory` нормализуются через `catalog_id_mappings`. Поэтому правила, созданные со старым ID или с названием подкатегории, продолжают совпадать с текущими каноническими значениями Rails. Для фиксированной цены достаточно выбрать подкатегорию «Худи и толстовки», оставить тип расчёта «Фиксированная цена» и указать 24 000 ₽; цена применяется сервером после AI, даже если модель не вернула `price_rule_key`. При повторной AI-обработке уже установленная положительная или ручная цена сохраняется, а цена `0` считается неназначенной и может быть заполнена новым правилом.

## Перенос фотографий при публикации

Перед отправкой товаров в Rails каждое внешнее фото скачивается, преобразуется в WebP и сохраняется в настроенный S3 по пути `batches/{batch_id}/...`. Для SEO-перепубликации последней выгрузки имя строится как `{slug-товара}-{slug-фото}.webp`; для обычной публикации используется техническое имя партии. После `PutObject` наличие объекта проверяется через S3 API. Ссылки из собственного `S3_PUBLIC_DOMAIN` повторно не загружаются, кроме явной SEO-перегенерации.

Если хотя бы одно фото недоступно или не сохранилось в S3, публикация всей партии в Rails останавливается. Успешно перенесённые ссылки сохраняются в технической БД, поэтому следующий запуск повторяет только оставшиеся внешние фотографии. В Rails не передаются товары с внешними ссылками на фото.

Если Szwego-публикация содержит `videoUrl`, парсер сохраняет и обычные фотографии альбома, и техническую ссылку на видео. При публикации AdminYeezy скачивает ролик размером не более 150 МБ, через FFmpeg создаёт совместимый MP4 (H.264/AAC, максимум 1080 px, `faststart`) и WebP-постер, загружает оба файла в S3 и передаёт Rails поля `video_url` и `video_poster_url`. Для одинаковой исходной ссылки используется общий стабильный S3-ключ, поэтому один ролик не дублируется между товарами и повторными публикациями. Ошибка конкретного видео не скрывает фотографии и не останавливает остальные товары: она сохраняется как предупреждение публикации, а повторный запуск может снова перенести ролик.

Для каждого фото автоматически выполняются до трёх попыток скачивания, преобразования, загрузки и проверки. Повторное нажатие «Пуш» снова проверяет оставшиеся ссылки.

Редактор партии работает отдельной страницей `/admin/batches/{batch_id}`, а не временной модалкой. Прогресс публикации хранится как серверная операция и остаётся видимым после закрытия страницы. Кнопка остановки ставит запрос на корректное завершение между товарами; потерянная после перезапуска контейнера блокировка считается зависшей через пять минут и может быть безопасно сброшена или автоматически перехвачена повторным запуском.

До переноса фотографий AdminYeezy проверяет непустые `external_id` через Rails admin API пачками до 50 значений. Если точный `external_id` уже есть в основном каталоге, товар полностью пропускается: его фотографии не скачиваются, существующая карточка не обновляется. Новые товары импортируются синхронными пачками до 50 строк: партия получает статус `Запушено в БД` только после фактического ответа Rails, а итоговое окно показывает реальное количество добавленных и пропущенных товаров.

Кнопка публикации имеет два режима:

- `Добавить новые` пропускает уже существующие в Rails `external_id`;
- `Обновить и добавить` полностью обновляет существующие карточки и добавляет новые.

Успешная публикация каждого Rails-чанка сразу фиксируется в `batch_publications`. Поэтому после сетевого сбоя повторный запуск продолжает работу без потери информации о уже созданных товарах. Для обычных новых выгрузок и обычного пуша старые объекты S3 не удаляются. Удаление неиспользуемых объектов выполняется только после успешной публикации явного запуска `Сгенерировать alt + slug` для самой последней выгрузки и только внутри префикса этой партии; общие фотографии сохраняются, чтобы не оборвать ссылки другой карточки.

## Дата публикации у поставщика

При создании новой альбомной выгрузки парсер сохраняет дату исходной публикации в `products.supplier_published_on` и во все JSONB-снимки партии. Сначала используются поля ответа Szwego, затем подпись товара и, если нужно, страница карточки. Относительные подписи (например, «17 минут назад») нормализуются в текущую московскую дату. AI, ручное редактирование, откат и публикация сохраняют это поле. В Rails оно передаётся отдельным `metadata.supplier_published_on`, в то время как `published_at` означает время пуша в каталог. Старые выгрузки не изменяются и показывают пустое значение.

## Целостность и восстановление

- Парсер создаёт партию, товары, сырой JSONB-снимок и связь с задачей одной транзакцией. Частично созданная партия откатывается целиком.
- Один поставщик может иметь только одну задачу парсинга со статусом `running`. Зависшая более 12 часов задача переводится в ошибку перед новым запуском.
- Для одной партии одновременно разрешена только одна операция: скрипт, AI, публикация, откат или удаление. Ручное редактирование во время обработки блокируется.
- Постобработка сохраняет товары, этап, снимок и запись истории одной транзакцией. Она всегда читает первый сырой снимок, поэтому повторный запуск не уничтожает китайский исходник.
- Просмотр снимка является только чтением и никогда не восстанавливает или не заменяет текущие товары автоматически.
- Официальные снимки `Сырой товар` и `Обработан скриптом` сохраняются. Для повторных технических AI-снимков хранится не более 10 последних снимков каждого типа.
- `batch_id` и непустой `external_id` обязательны для каждого технического товара; завершённая scraping-задача обязана ссылаться на существующую партию.
- При публикации перенесённые S3-ссылки фиксируются после каждого товара. Повторный запуск проверяет уже загруженные объекты и продолжает с оставшихся фотографий.

## Предложения справочников

Для трёх поставщиков Chromoff AI дополнительно получает отдельный справочник
активных категорий Chromoff. Выбранный `chromoff_category_id` сохраняется в
metadata товара и используется при публикации в `ChromoffListing`; общая
категория YeezyUnique при этом не подменяется. Низкая уверенность (ниже 0.75)
помечает listing как `needs_review` и не публикует его автоматически.

После AI отдельный экран показывает предложения новых подкатегорий, атрибутов и цветовых семейств. Для цветового семейства отображаются модель, найденные цвета, количество товаров, первые фотографии и габариты; служебный JSON свёрнут в блоке `Технические данные`. До одобрения исходная подкатегория, неизвестный атрибут и цветовое семейство не применяются.

В окне предложений доступны массовые действия `Принять всё` и `Отклонить всё`. Отклонение помечает все ожидающие предложения текущей партии как отклонённые одной операцией и не меняет товары.

В настройках поставщика в группе `Постоянные настройки AI-обработки → Предлагать` можно отдельно включить предложения новых подкатегорий и атрибутов. Оба переключателя выключены по умолчанию: AI по-прежнему выбирает существующие значения, но новые предложения не создаются.

В фильтрах товаров партии доступен режим `С видео`/`Без видео`. Видео определяется по исходной или уже перенесённой ссылке `video_url` в атрибутах товара.

## Библиотека шаблонов замеров

Внешние скриншоты размерных сеток не смешиваются с альбомами поставщика. На
странице `/admin/measurement-templates` оператор один раз загружает скриншот,
может распознать его через настроенный OpenRouter/BYESU AI, проверяет
структурированную таблицу (размеры, колонки, единицы и заметку) и
сохраняет её по типу одежды и конкретному поставщику. В карточке выгрузки
видны только шаблоны поставщика текущей партии. Во время полной AI-обработки
система автоматически применяет единственный шаблон подходящего типа к товару
того же поставщика: штаны, шорты, худи, зип-худи или вафельный лонгслив.
Тип определяется по новому названию, H1 и подкатегории товара, а не по
описанию. При нескольких шаблонах одного типа или неоднозначном товаре замеры
не меняются. ИИ-таблица замеров, прочитанная непосредственно с фото товара,
имеет приоритет. Ручное применение заменяет только `attributes.measurements`,
не меняя описание, изображения и видео; строки таблицы одновременно записываются
в `attributes.sizes`, чтобы основной сайт построил варианты/табы `S`, `M`, `L`,
`XL` и т. п. Существующие размеры не затираются, а объединяются с размерами
шаблона.

В основном каталоге тот же шаблон можно выбрать в панели массовых действий и
назначить отмеченным опубликованным товарам. Операция сохраняет остальные
`catalog_attributes` каждого товара и добавляет таблицу замеров и её размеры.

При распознавании AI получает не уменьшенную плитку контакт-листа, а
подготовленный сервером фрагмент исходного скриншота: белые поля обрезаются,
сама таблица увеличивается и передаётся непосредственно в запросе к модели.
Затем второй запрос с тем же изображением независимо сверяет размеры, форму
сетки и значения ячеек; переводы китайских названий параметров могут
отличаться и не считаются расхождением. Если данные сетки не совпадают,
таблица не применяется. Он переносит в ячейки только точные значения внутри
сетки. Ответы OpenAI-совместимых провайдеров приводятся к одному текстовому
потоку даже если `message.content` пришёл массивом, после чего из markdown или
поясняющего текста извлекается JSON и нормализуется к форме
`{unit,columns,rows,note}`.
Примечания вроде «ручное измерение, допустима погрешность 1–2 см» сохраняются
только в поле заметки к таблице: значение `86` не превращается в диапазон
`86–90`. Если AI не может уверенно прочитать сетку, он возвращает ошибку и не
подставляет типовую размерную таблицу; оператор может загрузить более чёткий
скриншот или заполнить поля вручную.

В карточке товара выгрузки цветовую семью можно исправить вручную: создать семью из выбранных товаров, добавить товары в текущую, привязать товар к уже существующей семье или отвязать его. При создании обязательно указывается название; оно хранится в `variant_group_name` вместе со стабильным `variant_group_key` и показывается в заголовке семейства. В просмотре выгрузки кнопка `Семейные группы` открывает список всех семей с названием и числом товаров; при открытии семьи видны её карточки. Массовый выбор также позволяет создать новую именованную семью из выбранных товаров или добавить их в существующую.

При одобрении:

- подкатегория создаётся в Rails со статусом `needs_review` и назначается товарам текущей выгрузки;
- атрибут добавляется в Rails-реестр и применяется затронутым товарам;
- цветовое семейство получает общий стабильный `variant_group_key`.

## Миграция

```bash
npm run db:migrate:scraping
```

Полная миграция создаёт папки, снимки, AI-очередь, предложения, ценовые правила, библиотеку шаблонов замеров, worker state, блокировки операций и реестр публикаций; она также добавляет ограничения целостности и удаляет таблицы `scraping_v2_*`.
