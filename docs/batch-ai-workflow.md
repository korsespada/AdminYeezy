# AI-обработка китайских товаров в «Выгрузках»

Раздел `/admin/batches` — единый production-конвейер китайских товаров. Экспериментальный `/admin/exports-v2` удалён вместе с таблицами `scraping_v2_*`.

## Этапы

Каждая выгрузка проходит четыре отображаемых этапа:

1. `Сырой товар` — результат парсера поставщика с китайским текстом и всеми фотографиями.
2. `Обработан скриптом` — поставщик-специфичный Python-скрипт удалил служебные карточки, объединил альбомы, переставил фотографии или заполнил известные поля.
3. `Обработано ИИ` — мультимодальная нормализация карточек и SEO.
4. `Запушено в БД` — отдельная ручная публикация в Rails-каталог.

После сырого импорта, скрипта и AI сохраняется снимок товаров. Действие «Откатить к этапу» восстанавливает выбранный снимок и удаляет более поздние снимки и AI-запуски. Оно нужно, если результат скрипта или AI не подходит; обычное редактирование отдельного товара отката не требует.

## Провайдеры AI

В `/admin/ai-rules` можно добавить сторонний OpenAI-compatible или Anthropic-compatible провайдер: название, Base URL и API-ключ; модель указывается только если endpoint не предоставляет `/models`. Отдельного поля «Тип» нет: протокол определяется автоматически по домену и URL. OpenRouter, BYESU и обычные совместимые сервисы используют `/chat/completions`; Anthropic и AgentRouter используют Messages API `/messages`, а для AgentRouter добавляется требуемый beta-маршрут. Base URL можно указывать без конечного endpoint (например, `https://openrouter.ai/api/v1` или `https://agentrouter.org/v1`). После добавления AdminYeezy пытается получить `/models`; список можно обновить кнопкой рядом с провайдером. Для сохранённого провайдера доступны проверка подключения и редактирование; при редактировании пустой API-ключ сохраняет прежний ключ. API-ключ хранится в `ai_providers.api_key_ciphertext` с AES-256-GCM и не возвращается в браузер.

Для шифрования требуется секрет окружения `AI_PROVIDER_ENCRYPTION_KEY`. Если сохранённый провайдер не выбран, сохраняется прежняя совместимость с `OPENROUTER_API_KEY` и `BYESU_*_API_KEY`. Удаление провайдера очищает его выбор; уже запущенные AI-задачи продолжают использовать snapshot без хранения открытого ключа.

Тайм-аут запроса к провайдеру по умолчанию 300 секунд и настраивается через `BYESU_TIMEOUT_MS`, `OPENROUTER_TIMEOUT_MS` и `ANTHROPIC_TIMEOUT_MS`. Тяжёлая карточка (десятки тысяч токенов промпта вместе со справочниками и рассуждениями модели) обрабатывается минутами: замер на выгрузке `Мужская одежда 2` дал 127–152 с на товар и 13–14 тысяч токенов рассуждений, поэтому прежний лимит 120 с обрывал запрос на середине. Такой тайм-аут теперь остаётся тайм-аутом и в сообщении (`… не ответил за 300 с (тайм-аут запроса)`), и в классификации повторов: batch AI повторяет запрос до трёх раз, а обычные временные ошибки — до пяти. Раньше тайм-аут подписывался как «Не удалось подключиться к BYESU (23)» и не повторялся, потому что повтор искал только англоязычные маркеры.

## Кастомные скрипты поставщиков

Основное хранилище этапов — `products` и JSONB-таблица `batch_snapshots`.

1. `SzwegoParser.py` возвращает массив товаров в JSON.
2. При импорте каждому товару присваивается неизменяемая исходная позиция `source_position`.
3. Python post-process получает JSON через stdin и возвращает JSON через stdout.
4. Результат сохраняется в `products`, партия получает этап `SCRIPT_PROCESSED` и JSONB-снимок.

Порядок особенно важен для скриптов, объединяющих соседние альбомы. CSV автоматически не создаётся и остаётся только ручным форматом экспорта. Старые скрипты подключены к единому runner; новые скрипты должны реализовывать `process_products(products)`. Для новых поставщик-специфичных изменений код не добавляется в образ: оператор сохраняет версию через настройки поставщика, проверяет её на raw snapshot через Preview и активирует. Версии хранятся в `supplier_post_process_scripts`; активная версия используется и при ручном, и при автоматическом запуске. Имя legacy-файла в `scripts/parser/` остаётся fallback, пока у поставщика нет активной версии из БД.

В плитке товара выгрузки в левом нижнем углу показан `#` исходного альбома (`source_position + 1`). Номер не меняется после постобработки и позволяет сверить карточку с сырой лентой поставщика.

Для поставщика `CH Одежда` (`_Z4krSCEyDqn5hvTYMJDEp4rykS4WwC0I`, supplier 5) используется `process_ch_clothing_timeline.py` вместе с источником `Единая лента`; активная версия хранится в `supplier_post_process_scripts`. Продукт закрывается разделителем `➨`, а товаром становится альбом с брендом `Chrome Hearts`/`克罗心`, полным описанием и 4 фото (в выгрузке 15.10 — 54 карточки). Сервисные альбомы поставщик публикует перед карточкой: `尺码表`, `实拍视频`, фото на моделях (`上身图参考`, `搭配`, `look`, «明星同款»), `标配：配套YB雪梨纸 手提袋+6` и `局部细节参考`. Из обложки остаются 1-е и 3-е фото (2-е и 4-е — те же кадры под углом), затем идут детали, потом фото на моделях, последней — размерная сетка. Упаковка и однофотонные текстовые альбомы (`三色`, `四色齐`, `原版级绣花一致`, `面料 五金自行对比`) не публикуются, а блоки из одного альбома (`‼️今日份资讯分享‼️`, `‼️原版开发‼️…`, `一系列 齐码现货`) товара не дают вовсе. Видео берётся своё; если на цветовую семью оно одно — копируется всем её карточкам, как и общая размерная сетка. Карточки одной модели в разных цветах (совпадающий текст после снятия цветовых слов) получают общий 32-hex `variant_group_key` даже через `➨`, а модели, отличающиеся типом вещи (`短裤`/`长裤`, `短裤`/`卫裤`/`套头`/`连帽`), остаются разными товарами. В редакторе карточки можно вручную заменить ссылку видео; ручная ссылка имеет приоритет и будет перенесена при публикации, постер создаётся из самого ролика. В сетке партии технические `attributes` скрыты, но остаются доступны в редакторе карточки.

Для `Chanel Сумки` (`_dmTrSFHqEWfdIw-LMbwscczrR7MF5hAU6p_QQHQ`) `process_chanel_bags_timeline.py` читает единую ленту как блок «упаковка → видео → основной альбом → детали», но выводит галерею как «основной альбом → детали → упаковка». Если сначала опубликован технический альбом с крупными планами, а следующий совпадающий альбом содержит содержательное описание товара, второй альбом становится главным и переносится в начало галереи. К одному основному альбому присоединяется только первый следующий короткий альбом деталей: последующие короткие карточки с тем же ярлыком считаются lookbook/фотосессией на другом фоне и исключаются, а не становятся самостоятельным товаром. При включённом `Парсинг тегов` исходный ярлык сохраняется в `attributes.szwego_tags` и является обязательным ключом склейки; старые снимки без него склеиваются только при точном совпадении артикула. Общая китайская рекламная фраза никогда не является доказательством одного товара. Поэтому аксессуар без деталей остаётся самостоятельным товаром с основной галереей, упаковкой и видео. Описание упаковки исключается, а ссылка видео сохраняется в `attributes.szwego_video_url`. Коллажи/сравнения и посты `合集`, `ZP`, первой/финальной версии, качества или разработки не становятся товарами. Совпадающие URL фото удаляются мгновенно; URL-разные визуальные дубли остаются для AI-очистки галереи и не задерживают постобработку.

Для `Dior Сумки` `process_dior_bags_timeline.py` работает с `全部 / единая лента` без `szwego_tags`, потому что их нет у видео-альбомов. Товаром становится фотоальбом с описанием, начинающимся с `【…】`. Видео в пределах трёх исходных позиций назначается следующему товару; если два и более таких товара имеют общий префикс названия модели и отличаются цветом, это одна цветовая семья и видео копируется во все её варианты. Альбом без подписи сохраняется только внутри уже доказанной цветовой семьи, между её подписанными вариантами; обзорный альбом перед семьёй не публикуется. Скрипт не объединяет фото вариантов и не прикрепляет видео к позднему несвязанному товару.

Для `Женская одежда 5` `process_womens_clothing_5.py` берёт из каждого
подтверждённого товарного блока содержательную карточку с сезонным кодом и
ставит её альбом первым. После него добавляются максимум два ближайших
альбома с содержательным описанием деталей; их описания дописываются к
описанию основного товара. Короткие служебные альбомы (`GW`, `Show`, `大图`,
`大图 细节`, `搭配/look`, `系列`, `全套礼盒` и похожие) вместе с фотографиями
не сохраняются. Фото соответствующей однокадровой таблицы/ценовой карточки
добавляются последними. Таблицы сопоставляются по бренду и пересечению
названия товара; timestamp используется только как порядок исходной ленты.
Очки и другие альбомы с признаками eyewear удаляются, как и одежда без
распознанного бренда. `BV`/`BVLG` определяется как Bottega Veneta.
Повторяющееся первое фото двух товарных карточек удаляется из обеих галерей.

Для `Женская одежда ZP 2` DB-backed post-process делит единую ленту по
`✨✨✨ ✨✨分割线✨✨✨ ✨✨` и оставляет только альбомы от пяти фотографий с
`随意实拍` в описании. Каждый такой альбом остаётся отдельным товаром, даже
если у нескольких альбомов один тег: это позволяет сохранить разные цвета.
Финальный альбом с ценой, `顶版`/`出货` и `码数` даёт описание и остальные
текстовые поля. Таблица `尺码表`/`尺寸表`/`尺码` из того же блока добавляется
в конец только при пересечении `szwego_tags`; её источник записывается в
`attributes.size_chart_source_id`. `external_id`, `source_position` и порядок
фотографий галереи сохраняются; служебные, модельные, упаковочные и
`挂拍对比图` альбомы не публикуются. Текущая версия хранится в
`supplier_post_process_scripts` и проверяется Preview на raw snapshot.

Для `Женская одежда 3` блок начинается разделителем `•••提莫·TIMO ...`.
Финальный содержательный альбом блока (позиция 16 на типовом скриншоте)
содержит описание и бренд, а карточка непосредственно перед ним (позиция 15)
становится товаром и сохраняет свои фото и identity. Альбом `下单尺寸表`
из этого же блока (позиция 8) добавляется последним в галерею и получает связь
`attributes.size_chart_source_id`. Служебные и промежуточные альбомы не
публикуются; товары с canonical-брендом Chrome Hearts также полностью
отбрасываются. При отсутствии бренда или основной галереи блок пропускается.

Если для поставщика в настройках заведены включённые Szwego-теги, запуск `Единая лента` доступен только после выбора одного тега в модальном окне выгрузки. Выбранный тег применяется к самой выгрузке: карточки без этого тега отбрасываются при чтении полной ленты. Поставщики, у которых теги не заведены и чей post-process рассчитан на поток без тегов, сохраняют прежний режим.

## Папки

Папка создаётся вручную и объединяет независимые выгрузки разных поставщиков. Поставщики не запускаются группой. Выгрузку можно перемещать между папками или вернуть в «Без папки». Удаление папки не удаляет выгрузки.

## Изображения

Фото включаются отдельно у каждого поставщика. Если настройка выключена, AI получает только исходный текст и не распознаёт визуальные таблицы размеров. Если включена, изображения отправляются contact sheet по девять кадров, сеткой 3×3; для длинной галереи создаётся несколько листов. Нумерация сквозная.

Если AI по contact sheet распознаёт фото как таблицу размеров, сервер автоматически
запрашивает до трёх соответствующих оригиналов для повторной проверки — даже
когда общий переключатель глубокого уточнения выключен. Для пары `Size Chart` и
`Size Recommendation` повторная проверка требует распознать обе таблицы.

В настройках поставщика можно включить `Поставить лучший кадр первым`. Тогда AI возвращает номер лучшей фотографии, сервер переносит только её в начало галереи, а порядок остальных кадров сохраняет. Поставщик может дополнительно хранить визуальные эталоны ракурсов: оператор загружает или вставляет изображение из буфера обмена, указывает подпись и пояснение. Эталоны передаются отдельным contact sheet и используются только для оценки типа и качества ракурса; они не являются фотографиями текущего товара и не подтверждают его бренд, цвет, материал или размер.

Опциональное «Уточнение по оригиналу» разрешает второй vision-запрос только при низкой уверенности: AI выбирает до трёх кадров с плохо читаемым логотипом, брендом или моделью и получает их в исходном размере.

При обычной AI-обработке, если у поставщика включены фотографии, alt создаются в том же первом vision-проходе, что и карточка товара. Второй vision-запрос для alt не выполняется. Если обработка фотографий у поставщика выключена, alt заполняется названием товара. Для уже опубликованной **самой последней** выгрузки доступен отдельный запуск `Сгенерировать alt + slug`: перед запуском AdminYeezy получает из Rails финальный slug товара с внутренним SEO-артикулом. Затем AI получает contact sheet 3×3 и возвращает только alt, не запрашивая каждую фотографию отдельно. Slug фото сервер строит транслитерацией соответствующего alt, сокращая его до 120 символов и добавляя номер только при совпадении. Уточнение по оригиналам в этом режиме отключено. Slug товара строится как `бренд-название-внутренний-артикул` в латинице; модель и цвет отдельно не добавляются — адрес собирается из названия, а `external_id` в slug не входит. Alt всегда содержит подтверждённый бренд, пишется по-русски с целевой длиной 60–120 символов и жёстким максимумом 160. Alt виден в браузерной подсказке при наведении на фото в карточке товара.

AI может:

- исключить рекламу, дубли и нерелевантные кадры из публичной галереи. Фото с основным товаром рядом с упаковкой или другим товаром сохраняется, если основной товар хорошо виден и остаётся главным объектом; исключаются только кадры, где посторонний объект доминирует или делает товар неясным. Крупный наложенный промо-/информационный текст, цена или призыв на любом языке исключает кадр, а небольшой логотип или водяной знак — нет;
- определить таблицу размеров, извлечь размеры и не публиковать саму таблицу. Если таблица не относится к основному товару или подтверждённой части комплекта, AI исключает её через `discard_indexes` и не использует её значения. Для обычного товара сохраняется ровно одна таблица замеров в `measurements`; если на одном изображении есть также таблица подбора по росту и весу, она сохраняется отдельно в `size_recommendation` и не превращает диапазоны роста/веса в размеры товара. Только у подтверждённого комплекта с отдельными читаемыми таблицами замеры сохраняются как `measurements.tabs` с однословным названием каждой вещи. На витрине вкладки показываются только для такого набора таблиц;
- сопоставить признаки на фото с китайским текстом.

Фото таблицы всегда удаляется из публичной галереи, если AI определил кадр как
таблицу размеров или рекомендаций, даже при неполной нормализации данных.
Для изображения с парой `Size Chart` + `Size Recommendation` AI по возможности
заполняет `attributes.measurements` и `attributes.size_recommendation`; отсутствие
одного из полей не возвращает фото в галерею. При повторном запуске «из
исходника» используются оригинальные фотографии исходного batch. При отсутствии
`price_rule_key` цена берётся из инструкции поставщика по ценам
(`choosePriceFromAiInstructions` в [lib/batch-ai.ts](../lib/batch-ai.ts)).
ИИ видит всю инструкцию и выбирает строку по смыслу, поэтому его цена
используется первой, если она есть среди цен инструкции. Иначе сервер ищет
строку по словам, но только среди коротких строк до 40 знаков без `;`, скобок
и «не …» (например, `Футболки — 21000`). Каждое значимое слово условия должно
начинать слово товара, числа не учитываются. Длинные строки-условия вида
«Футболка или поло из кашемира, шерсти…; не 100% хлопок» понимает только ИИ:
прежний поиск по любому слову нашёл «пол» внутри «наполнитель» и поставил
пуховику цену футболки. Нулевое универсальное правило не затирает найденную
цену из этой инструкции; явное ненулевое ценовое правило имеет приоритет.

Исходный текст считается ненадёжным: он может относиться к соседней карточке или другой модели. При включённых фотографиях AI сначала определяет согласованный товар по всей серии кадров, а затем проверяет текст. Если источники прямо противоречат друг другу, модель, тип товара, цвет, материал, фурнитура, классификация и публичные тексты строятся по фотографиям; противоречащая часть текста отбрасывается. Если фото лишь не позволяет рассмотреть материал или деталь, это не считается противоречием: явно указанный технический факт сохраняется. До трёх оригиналов разрешено запросить не только при низкой общей уверенности, но и для разрешения конфликта текста и изображений.

Если первый AI-ответ при включённых фото называет одежду комплектом, сервер запускает обязательную повторную визуальную проверку. В ней сохраняются JSON-схема и справочники, но блок исходного товара исключается: упоминание `套装`, цена либо таблица с верхом и брюками не доказывают вторую вещь. Комплект сохраняется только когда на серии кадров отчётливо видны минимум две разные вещи; иначе AI описывает и классифицирует единственную вещь, а таблицу помечает только как таблицу замеров.

Исходные фотографии остаются в снимке этапа и восстанавливаются откатом.

Если AI исключает все фотографии товара как нерелевантные или являющиеся скриншотами, сервер сохраняет карточку с пустой публичной галереей для ручной проверки, а исходные фотографии остаются в снимке этапа. Они не возвращаются автоматически в обработанную карточку.

## Результат AI

В технической БД до публикации сохраняются:

- видимые `name` и `h1` (без бренда, но с цветом) и `description`;
- существующие ID бренда, категории и подкатегории;
- пол и структурированные `attributes`;
- `translations.en` с `name`/`description` и `photo_alts_en` для английской
  витрины;
- уверенность, ошибка отдельного товара и предложение цветового семейства.

Колонки `translations` и `photo_alts_en` добавляет `npm run db:migrate:scraping`
(скрипт `migrate-batch-ai.js`). EN-поля сохраняют оба пути AI-обработки:
`applyCompletedItem` и разделение по цветам. До 2026-10-22 путь OpenRouter/BYESU их терял, а публикация не читала
`translations`/`photo_alts_en` из БД, поэтому EN-версия не доходила до Rails.
Экран выгрузки загружает перевод вместе с товаром и сохраняет его при правке
в карточке (переключатель RU/EN в шапке); скрипты постобработки и импорт
перевод не стирают. При публикации `translations.en` и EN-alt уходят в Rails
и при создании (import API), и при обновлении существующего товара; если
перевода нет, публикация не блокируется. До миграции worker сохраняет результат
AI без EN-полей и пишет предупреждение в лог, а не падает. Повторная публикация
не затирает перевод, отмеченный в Rails проверенным: import API сам сохраняет
проверенный перевод, пока русский текст не изменился, а при обновлении AdminYeezy
не отправляет `translations` товару, у которого в Rails `translations.en.status`
равен `reviewed`, потому что обновление записывает перевод без этой защиты. Полнота EN-перевода товара —
название и описание; `h1`, title и meta на EN витрина собирает из EN-названия.
Статус перевода и кнопка «Отметить проверенным» есть в карточке товара и на
экране «Переводы» (`/admin/translations`). Категории там показаны деревом,
с фильтром по состоянию, счётчиком «проверено N из M», русским оригиналом
и массовым «Отметить проверенными»; редактор включает `seo_text_top` и
`seo_text_bottom`. Порядок для категорий: импорт названий → AI длинных
текстов → проверка. После AI статус становится `machine`, поэтому категория
индексируется на EN только после отметки «проверено».

Для последней выгрузки отдельный режим `Сгенерировать alt + slug` перезаписывает в технической БД `slug`, `photo_alts` и `photo_slugs`. Он не меняет название, описание, цену, классификацию, атрибуты и публичную галерею до отдельной публикации. AI не создаёт новые бренды или верхнеуровневые категории.

## Запуск и повторная обработка

Отдельного теста на первых 10 товарах нет: кнопка «Обработать ИИ» на странице выгрузки и в списке выгрузок сразу обрабатывает все ещё не обработанные товары. Каждый запуск берёт текущие глобальные провайдер, модель, промпт, temperature и max tokens из `/admin/ai-rules`; повторный запуск после остановки называется «Продолжить ИИ» и тоже читает текущие настройки. До запуска сохраняется снимок `До AI · full`.

Версию товара до обработки можно посмотреть в карточке: переключатель «После ИИ / До ИИ» в шапке загружает по запросу только этот товар из последнего снимка, где он ещё не обработан (`getBatchProductBeforeAiAction`). Остальные необработанные версии не загружаются. Версия до ИИ открывается только для просмотра.

Ошибки одного товара не останавливают остальные. Ошибочный или уже обработанный товар можно запустить повторно; перед повтором также создаётся снимок.

Для партии со статусом `Запушено в БД` доступна кнопка `Переобработать ИИ`. Она создаёт снимок опубликованного состояния, помечает выбранные товары ожидающими AI, применяет текущие настройки, промпт и справочники и переводит успешно завершённую партию обратно в `Обработано ИИ`. Существующая цена и `price_source` сохраняются. После проверки результат публикуется режимом `Обновить и добавить`, поэтому Rails-товары с тем же `external_id` обновляются без создания дублей. Можно переобработать всю партию или только выбранные после фильтрации.

Действие `Восстановить таблицы замеров` не переобрабатывает карточки и не снимает с партии статус `Запушено в БД`. Оно объединяет сохранённые скриптовые связи одежды и обуви с исходными фотографиями таблиц, распознаёт каждую уникальную таблицу один раз и записывает `attributes.measurements` и размеры строк в `attributes.sizes` в связанные товары, где замеров ещё нет. Названия, описания, цены, классификация, цвета и публичные галереи при этом не меняются.

При обновлении ранее опубликованной партии фотографии, уже находящиеся в S3 или прикреплённые к существующему Rails-товару с тем же `external_id`, используются повторно. После `Сгенерировать alt + slug` ближайшее действие `Обновить каталог` один раз перевыкладывает фото последней партии в WebP под именами `{slug-товара}-{slug-фото}.webp`, передаёт в Rails slug и alt каждого изображения, а после успешной публикации удаляет устаревшие файлы только из S3-префикса этой партии. Успешно применённый SEO-запуск помечается опубликованным и не вызывает повторное перекодирование или удаление при следующих обычных пушах. Если у старой партии сохранились исходные внешние URL, а доступ к бакету не настроен, режим `Обновить и добавить` сохраняет текущую Rails-галерею и обновляет остальные поля. `S3_BUCKET` требуется только для переноса действительно новых внешних фотографий.

Общий системный промпт не содержит классификацию всех возможных категорий. Отдельные наборы из редактируемого реестра `Автоматические правила категорий` подключаются к запросу для установленной категории; если исходная категория не определена или в запросе доступно несколько категорий, AI получает все настроенные правила и выбирает нужное после визуального определения товара. Эти правила имеют приоритет над инструкцией поставщика. Перед сохранением сервер дополнительно сверяет смысл названия и описания с выбранной подкатегорией и исправляет явное противоречие на существующее значение справочника. При такой проверке тип из названия товара приоритетнее слов внутри описания; описание используется, только если название типа не содержит. Детерминированная проверка сопоставляет только самостоятельные названия типов товара: служебные фразы внутри описания, например «комфорт в носке», не должны менять подкатегорию. В `Настройках ИИ` оператор может создать категорию или подкатегорию в Rails, добавить для категории отдельное правило, изменить его текст или удалить. Категория и подкатегория становятся доступными AI сразу после создания, а текст правила — после `Сохранить настройки`; AI выбирает только уже сохранённые значения и не создаёт их самостоятельно.

### Адаптивная глубина описания

Перед каждым AI-запросом приложение строит профиль источника по длине
содержательного текста, количеству технических признаков и наличию фотографий.
Для богатого технического описания AI получает цель 500–800 знаков и обязан
сохранить все подтверждённые материалы, технологии, конструкцию, точные цвета,
маркировки и расположение деталей. Для смешанного источника целевой диапазон
350–650 знаков: текст дополняется только видимыми признаками. При коротком
или рекламном тексте фотографии становятся основным источником, а описание
сокращается до 250–500 знаков без догадок о составе, технологиях и скрытой
конструкции. Поэтому один общий предел длины не применяется ко всем
поставщикам и карточкам.

Инструкция `Женская одежда 5` содержит только особенности китайского источника: удаление сезонных кодов из публичного текста, сохранение конкретных материалов и деталей из блока `细节`, а также требование к содержательному русскому описанию. Бренд этой выгрузки уже назначается постобработкой; AI должен сохранять установленное поле `brand` и не переопределять его по алиасам, китайскому тексту или фотографии. Инструкция не дублирует системную JSON-схему и не переопределяет правила категории «Одежда»: при конфликте действует системный промпт, затем глобальные правила каталога и правила категории, затем инструкция поставщика. Цены для новой схемы выбираются через `price_rule_key`; свободный маппинг цен в тексте инструкции поставщика не используется.

Для `Женская одежда 2` постоянная инструкция поставщика перечисляет только
повторяющиеся сокращения брендов и требует сохранять уже назначенный
постпроцессором canonical `brand`. Таблица размеров используется как
технический источник размеров и исключается AI из публичной галереи; общие
рекламные фразы не считаются характеристиками. Это не заменяет системную
JSON-схему и правила категории «Одежда».

В классификации одежды визуально подтверждённый тип имеет приоритет над
словом `套装`: «Комплекты» допустимы только при двух разных вещах на фото.
Платья (включая мини, миди, макси, платье-поло и платье-футболку) и
комбинезоны/ромперы относятся к «Платья», юбки — к «Юбки», джинсы — к
«Джинсы», а джинсовые шорты — к «Шорты». Два цвета одной вещи и повторные
ракурсы комплектом не считаются.

Для `Женская одежда 3` инструкция учитывает блоки TIMO и требует сохранять
непустой canonical `brand`, назначенный постобработкой. Из китайского финального
описания AI переводит только подтверждённые характеристики вещи; цены, коды
сезона/коллекции, Zp, заявления 1:1, рекламу и эмодзи в публичный текст не
переносит. Фото `下单尺寸表` используются только для размеров и исключаются из
публичной галереи. Инструкция не дублирует системную JSON-схему и правила
категории «Одежда».

Для `Муж Одежда` (supplier 71) инструкция описывает шаблонную подпись Szwego
«📍 Бренд - изделиеSize ：48-56Color ：Green Black Beige Brown», в которой
перечислены все цвета модели, а не только цвет карточки. Инструкция требует
использовать единственный цвет из уже заполненного поля `colors` и не
перечислять остальные цвета семьи в `name` и `description`, сохранять
назначенный бренд и не переносить в публичные тексты опечатки подписи
(например, `Brubello Cucinelli`), китайские слова модели, служебные обороты про
источник и сами шаблонные метки `Size`/`Color`/`📍`. Там же зафиксированы
наблюдаемые размерные ряды источника (48–56 у верхней одежды, 30–38 без 37 у
джинсов, M-3xl у футболок и поло), написание цветов поставщика и то, что часть
подписей вместо цвета содержит качество изделия (`Hand-made`, `Hand-knitted`).
Технические детали берутся только с фотографий, нижний кадр галереи —
размерная сетка; `color_family` не возвращается, потому что цветовые семьи
назначены постобработкой. Инструкция не дублирует системную JSON-схему, правила
категории и список цен поставщика.

Для `LP, Zegna, BC Мужская одежда` (supplier 28) постобработка подставляет в
описание товара альбом модели с пунктами «▫️» (состав, размеры, палитра,
комплектация, код модели). Без инструкции модель считала этот текст
ненадёжным и писала описание по фото: теряла «100% шерсть», комплектацию и
гусиный пух и добавляла кашемир, которого нет в составе. Инструкция
(2026-10-22) говорит доверять этому тексту, если фото ему прямо не
противоречат: состав брать только из «Состав материала», наполнитель писать в
`filling`, комплектацию и конструкцию переносить в описание, перечитывать все
колонки сетки на последнем фото, цвет карточки брать с её фото, а цену в юанях,
опт, «1:1», палитру, код модели и служебный тег не публиковать. Цены
поставщика остаются в отдельной инструкции по ценам.

Для поставщика `Обувь` инструкция учитывает китайские карточки Szwego: служебные
`Без бренда`/`Без названия`, повторённые заголовки, рекламные фразы и коды сезона
вроде `26ss` не считаются брендом, моделью или характеристикой. Термины
`鞋面`, `内里`, `大底`, `跟高`, `圆头`, `粗跟`, `平底`, `短靴`, `中筒靴`, а также
материалы `牛皮`, `牛反绒`, `羊皮` и `橡胶大底` переводятся как технические
характеристики обуви. Маркер `💰` и условие `定制不退换` не переносятся в
публичные поля. `szwego_tags` используются только как дополнительная подсказка,
а уже заполненные идентификаторы цветовых групп не переопределяются. Технические
детали из середины китайского описания не сокращаются до общих фраз: сохраняются
названия технологий и маркировок, сочетания материалов, раздельные признаки
`中底`/`大底`/`鞋面`, конструкция задника и точное расположение логотипов или
полосок. Пространственные признаки не переносятся на другую деталь: например,
полоски на внешней стороне промежуточной подошвы не описываются как полоски на
боковине верха.

Для поставщика `Обувь МЖ` карточки Hermes (`Hermes`, `爱马仕`) исключены до
AI-нормализации. У оставшихся карточек поле `brand` уже заполнено каноническим значением по
явному бренду в описании; непустой `brand` нельзя переопределять по тегу,
китайскому алиасу или фотографии. Переданный `variant_group_key` нужно
сохранять без изменений и не превращать в объединение карточек. В публичный
текст не переносятся исходные ценовые маркеры (`42.0`, `48.0`, `高帮`, `低帮`),
`牛货🔥`, `zp`, `1:1`, эмодзи, даты отгрузки и рекламные обещания. Термины
`鞋面`, `内里`, `大底`, `跟高`, `后跟可踩`, `乐福鞋`, `玛丽珍`, `人字拖` и
`夹脚` переводятся как технические признаки конструкции, а материалы
`牛皮`, `胎牛皮`, `小牛皮`, `羊皮`, `胎羊皮`, `麂皮` и `牛反绒` сохраняются
только в подтверждённом значении. Инструкция не дублирует JSON-схему и общие
правила категории «Обувь».

### Повторный поиск цветовых вариантов

После полной AI-обработки рядом с кнопкой публикации доступна кнопка `Найти варианты`. Это отдельный AI-запуск с режимом `variants`, а не повторная SEO-обработка.

- Проверяются только товары с `ai_processed=true`, которым ещё не назначен `variant_group_key`.
- В модель передаются название, описание, бренд, категория, подкатегория, пол и уже сохранённые атрибуты. Фотографии, contact sheet, оригиналы и визуальные эталоны цен не передаются.
- Используются текущие глобальные провайдер и модель из `/admin/ai-rules`.
- AI возвращает только `color_family` или `null`. Название, SEO, цена, классификация, атрибуты и галерея товара не изменяются.
- Для сумок должны совпасть бренд, точная модель, габариты в том же порядке измерений, материал и фурнитура; для обуви — бренд, модель, конструкция и материал; для одежды — бренд, модель/фасон и материал. Цвет исключается из сигнатуры. Например, `30 × 26 × 14` и `26 × 30 × 14` считаются разными размерами.
- Сервер объединяет одинаковые сигнатуры и показывает предложение только при наличии минимум двух товаров и двух различных цветов.
- Если у поставщика включено `Проверять подряд идущие товары как цветовое семейство`, после успешной полной AI-обработки автоматически запускается поиск непрерывных групп из 2–8 обработанных карточек с одинаковыми брендом и категорией. Это запасной путь для поставщиков без надёжных артикулов: AI получает первые фото и метаданные соседних карточек, сравнивает фасон, принт, конструкцию и материал и возвращает только уверенные семейства. Разные модели в одной последовательности он обязан пропустить. Найденные семьи всегда остаются предложениями до ручного одобрения. Кнопка `Найти варианты` остаётся ручным повторным запуском.
- Поиск семейства не переносит и не объединяет фотографии: каждая карточка хранит только свою галерею и, при наличии, своё видео.

### Разделение одного альбома на цветовые товары

В карточке товара с двумя и более фотографиями доступна кнопка `Разделить по цветам`. Она делает один vision-запрос: AI распределяет фотографии отдельных экземпляров по цветам и в том же JSON заполняет отдельное видимое название каждого цвета без бренда, описание, классификацию, атрибуты, цену и alt каждого нового товара. H1 всегда равен `name`; title и meta description после публикации централизованно формирует Rails из бренда, названия и цены. Второй AI-проход для созданных карточек не выполняется.

Сервер проверяет, что получено от 2 до 8 уникальных цветов, одна фотография не назначена нескольким товарам и у каждого варианта есть фотография. Затем одной транзакцией исходный товар превращается в первый цвет, остальные создаются с детерминированными `external_id`, все сразу получают `ai_processed=true` и общий стабильный `variant_group_key`. Общие кадры с несколькими цветами можно не включать ни в один вариант. Если у исходного видео есть poster, он отправляется AI отдельным ненумерованным кадром: AI выбирает один из уже найденных `color_key`, и видео сохраняется у соответствующего варианта. Если цвет неясен или в превью несколько цветов, видео остаётся у первого варианта; оно никогда не копируется во все карточки. Режим доступен для BYESU и OpenRouter.
- Процесс можно остановить. Уже найденные предложения сохраняются.

### Постоянные настройки AI поставщика

В настройках поставщика (`Настройки AI поставщика` в меню выгрузки или `/admin/suppliers`) есть постоянный блок правил AI-обработки. Эти параметры не запускают отдельный постпроцесс: они сохраняются у поставщика и автоматически применяются к `Тесту 10 товаров` и `Полной обработке` всех его выгрузок.

- `Группировать по артикулу` принимает пример вроде `SP001 blue`; AI отделяет цвет от общей основы и формирует цветовую семью.
- `Проверять подряд идущие товары как цветовое семейство` после полной AI-обработки автоматически добавляет соседние карточки как кандидатов, даже когда артикул отсутствует или названия цветов различаются. Эта настройка не объединяет галереи; `Найти варианты` остаётся ручным повторным запуском.
- `Разделять разные цвета внутри одного альбома` выполняет разделение и полную обработку вариантов одним запросом. Если цветов нет, сохраняется одна обычная карточка.
- `Поставить лучший кадр первым` меняет только первое фото, остальные и их alt сохраняются в порядке.
- `Исключать альбом только с фото моделей` удаляет товар из текущей версии, но исходная карточка остаётся в снимке для отката.

Провайдер, модель, промпт и фактические параметры обработки записываются в `batch_ai_runs.settings_snapshot`, поэтому каждый запуск воспроизводим. При продолжении полной обработки используются актуальные постоянные правила поставщика.

### Видео поставщика

Парсер Szwego сохраняет обычные фотографии отдельно от ссылки видео, даже если API возвращает медиа вложенным объектом. Поддерживаются `videoUrl`/`videoURL`, вложенные `pvod/*.mp4` и poster/cover URL. В карточке выгрузки видео показывается отдельным плеером с poster и стандартными кнопками управления. При публикации `scripts/batch-workflow.js` сжимает исходник через FFmpeg в MP4 H.264/AAC, генерирует poster WebP и сохраняет оба объекта в S3; в Rails передаются `video_url` и `video_poster_url`.

После завершения автоматически открывается окно `Предложения ИИ`. Утверждение предложения назначает затронутым товарам общий `variant_group_key`; отклонение не меняет товары.

## Провайдеры

Глобальная настройка на `/admin/ai-rules` выбирает `BYESU`, `OpenRouter` или сохранённый совместимый провайдер. Эта страница является единственным интерфейсом глобальных batch AI-настроек; раздел выгрузок использует сохранённые значения.

- Все провайдеры вызываются сервером AdminYeezy; модель задаётся в интерфейсе.
- Системный и пользовательский промпты одинаковы для провайдеров.
- Количество одновременных запросов задаётся на `/admin/ai-rules`.

Локальный провайдер Cockpit и его worker (`scripts/batch-ai-worker.js`,
`/api/batch-ai/worker`, `COCKPIT_*`) удалены 2026-10-22. Если в
`app_settings.batch_ai_provider` осталось значение `cockpit`, оно читается как
`openrouter`, а в настройках Chromoff AI-SEO — как `byesu`. Таблица
`batch_ai_worker_state` и колонки аренды в `batch_ai_items` в схеме остались,
но больше не используются.

## Промпты

Итоговый контекст состоит из общего системного промпта, необязательной инструкции поставщика, справочников Rails, схемы атрибутов, исходного товара и, если разрешено, contact sheet. Инструкция поставщика хранит только особенности его ленты; полный отдельный промпт не требуется.

Глубина описания задаётся системным промптом (`app_settings.batch_ai_system_prompt`) и «Профилем исходных данных для описания» из [lib/batch-ai.ts](../lib/batch-ai.ts). Верхнего лимита нет: для богатого фактического источника ориентир — 900–2000 знаков, для среднего — 400–900, для скудного — 250–500, и все они означают минимальную глубину, а не максимум. Если подтверждённых фактов больше, описание пишется длиннее; богатый источник нельзя сокращать до общей фразы. Проверка профиля на выгрузке `09f879ba-749d-4143-b606-c489f4fe30bc` после склейки альбомов: у 282 товаров из 288 режим `rich_source` при длине исходного текста 243–2473 знака, у 6 — `balanced_source`.

Для поставщика `Пуховики, куртки, пальто, жилеты` (supplier 55) сохранена отдельная инструкция поставщика: описание должно быть полным изложением исходного технического текста (обычно 900–2000 знаков и 3–5 коротких абзацев) с переносом состава и наполнителя, конструкции и деталей, фурнитуры и маркировки, комплектации и упаковки, цветов и номера модели; рекламные обещания, себестоимость и заявления о подлинности не переносятся, иероглифы и транслитерация не сохраняются. Там же перечислены отдельные характеристики утеплённой верхней одежды, которые нужно заполнять, когда они названы в тексте: «Наполнитель», «Мех», «Воротник», «Капюшон», «Застёжка», «Пояс», «Длина изделия», «Материал подкладки».

### Размеры, замеры и характеристики одежды

Таблица замеров — источник размерного ряда товара. `applyMeasurementTableAttributes` в [lib/measurement-templates.ts](../lib/measurement-templates.ts) выставляет `sizes` равным размерам из колонки «Размер» и больше не объединяет их с уже записанными значениями: раньше AI читал общий справочник атрибута `sizes` (`S`, `M`, `L`, `XL`, `35–45`) и дописывал эти значения к фабричным размерам `1–4`, из-за чего у куртки с четырьмя размерами в карточке оказывалось восемь. Если в таблице нет строк с размерами, существующее значение не меняется. Поле `measurements.note` остаётся пустым: системный промпт и глобальные правила прямо запрещают пересказывать в нём размерный ряд.

Явный буквенный размерный ряд из текста поставщика («Размеры: M•L•XL•2XL•3XL»)
сверяется с таблицей (`textSizesMissingFromMeasurements`). Широкая таблица в
contact sheet мелкая, и модель может потерять крайнюю колонку даже при
повторной проверке оригинала: на товаре поставщика 28 таблица M–3XL была
прочитана как M–XXL. Если в таблице нет размера из текста, сервер ещё раз
отправляет оригинал сетки с прямым указанием, каких размеров не хватает, и
берёт из повторного ответа только сетку, если в ней стало меньше пропусков.
Если размер всё равно не прочитан, он остаётся в `sizes` без замеров, а в
`ai_error` пишется предупреждение с префиксом `Размеры:` (красная плашка в
карточке). Повтор выполняется
для OpenRouter и BYESU.

Для категории `Одежда` в [lib/catalog-attribute-schema.ts](../lib/catalog-attribute-schema.ts) добавлены характеристики верхней одежды: `filling` (Наполнитель), `fur_type` (Мех), `collar` (Воротник), `hood` (Капюшон), `closure` (Застёжка), `belt` (Пояс), `product_length` (Длина изделия), а `lining_material` расширен с обуви на одежду и обувь. AI заполняет их только при явном указании в тексте. Каждая характеристика несёт `parser_rules` с примерами (`goose down filling`, `detachable waist belt`, `特级鹅绒填充`), которые передаются AI в схеме атрибутов. Пока для нового кода нет значений в справочнике Rails, `getCatalogAttributeDefinitions` сохраняет список значений из встроенной схемы вместо пустого массива. Модель часто записывает пух и перо в `materials`, а не в `filling`; если `filling` есть в схеме товара и пуст, сервер (`moveInsulationToFilling`) переносит их в наполнитель: «Гусиный пух» или «Утиный пух» по тексту, «Пухо-перо», если упомянуты пух и перо, иначе «Пух».

### Повторные вызовы модели

Обработка одного товара может состоять из нескольких обращений к модели, и это не повторная обработка товара. Попытки видны в `batch_ai_items.attempts` (товар повторно берётся в работу, если предыдущая попытка вернула невалидный JSON), а внутри одной попытки `withBatchAiRetry` в [lib/batch-ai.ts](../lib/batch-ai.ts) повторяет запрос до пяти раз с паузами 1–30 секунд при `429`, `5xx`, таймауте или сетевой ошибке. Каждое такое обращение тарифицируется отдельно; журнал токенов и стоимости ведёт провайдер, в AdminYeezy он не хранится — здесь доступны только `batch_ai_runs` (запуск), `batch_ai_items` (товар, статус, число попыток, сохранённые `input_snapshot` и `output`) и ошибка попытки в `error_message`.

У поставщика категории, подкатегории и бренды задаются необязательными множественными ограничениями. Пустой список разрешает AI выбирать по всему справочнику. Непустой список ограничивает выбор указанными значениями, но не назначает первый вариант принудительно. Ограниченные подкатегории дополнительно фильтруются по родительской категории. Если поставщик разрешает только одну категорию, AI получает только её подкатегории. При нескольких допустимых категориях передаётся общий разрешённый список с `parent_id`, чтобы AI мог исправить ошибочную исходную категорию, а сервер проверяет соответствие подкатегории итоговой категории.

Глобальные правила каталога применяются поверх инструкций любого поставщика. Legacy-подкатегории `Туфли`, `Сумки` и `Кофты` не передаются AI в справочнике выбора; старые записи с ними сохраняются, но новый результат должен выбрать конкретный существующий тип. Для категории `Сумки` итоговая техническая подкатегория `Сумки` запрещена: AI обязан выбрать конкретную существующую подкатегорию. `Сумки-косметички`, `Сумки-кейсы`, `Сумки с клапаном`, `Сумки-багет`, `Мини-сумки`, `Сумки-боулинг`, `Пляжные сумки` и `Сумки с верхней ручкой` не создаются и не назначаются; такие результаты сервер автоматически переводит в `Сумки на плечо`. Сумки с короткой верхней ручкой также относятся к `Сумкам на плечо`. `Сумки-хобо` и `Сумки-тоут` сохраняются отдельными подкатегориями как устойчивые типы конструкции. Если AI всё равно возвращает общую подкатегорию `Сумки`, товар завершается с ошибкой и требует повторной обработки. `Caviar`, кавьяровая и зернистая кожа считаются фактурой и нормализуются в материал `Кожа`; подтверждённые `Кожа ягнёнка` и `Телячья кожа` сохраняются отдельными материалами.

Для всех поставщиков категории `Обувь` используется закрытый справочник конструкций и правила из [shoe-taxonomy.md](./shoe-taxonomy.md). Фотографии определяют тип обуви, а текст подтверждает размеры и материалы. AI не создаёт новые обувные подкатегории; известные синонимы вроде `Дерби`, `Сабо` или `Босоножки` автоматически сводятся к существующим группам. Слингбэки с закрытым мысом и задним ремешком относятся к `Туфли на каблуке` или `Туфли на плоской подошве`, а не к `Мюли и сабо`; сервер дополнительно нормализует явные признаки слингбэка после ответа AI.

Гендер обуви определяется AI по совокупности явного текста, полного размерного ряда, атрибутов и фотографий. Явное указание и `audience` у группы размеров имеют приоритет; размерный ряд используется как признак, а не как безусловный порог. Женские размеры могут доходить до 41, мужские часто начинаются с 39, а спорные ряды вроде `38–45`, `38–41` и `36–44` AI решает по контексту и фото либо возвращает пустое значение при недостаточной уверенности. Половинки сохраняются только при явном указании; из обычного `36–45` половинки не добавляются. Эта логика общая для категории, а не настройка конкретного поставщика.

Для категории `Одежда` также используется только существующий справочник подкатегорий. Известные названия и синонимы нормализуются сервером; при явном конфликте AI-ID с распознанным типом товара приоритет имеют название и описание, сформированные по серии фотографий. Например, жакет не сохраняется как `Штаны`, а переводится в существующую подкатегорию `Жакеты`. Неизвестный результат не создаёт предложение новой подкатегории: товар сохраняется без подкатегории и требует ручного выбора или повторной обработки после обновления справочника. Замшевые куртки относятся к существующей подкатегории `Кожаные куртки`, при этом материал `Замша` сохраняется отдельным атрибутом и в описании. `Дублёнки` — общая подкатегория для мужских и женских моделей; пол по-прежнему определяется отдельным полем `gender`.

В открытой выгрузке можно выбрать произвольные товары и запустить для них отдельную AI-обработку через массовую панель. Такой запуск не меняет статус всей партии. Во время выполнения над фильтрами показываются прогресс и ближайшие товары очереди с фотографиями. Фильтры по модели и цвету строятся по уже записанным атрибутам и включают варианты `Без модели` и `Без цвета`.

Кнопка отдельной карточки и массовое действие «Повторить ИИ из исходника» берут сохранённое состояние товара до его первого завершённого AI-запуска, а не уже переписанные русские поля. Массовое действие затрагивает только выбранные карточки. Поэтому можно точечно восстановить сведения, потерянные прежним AI-ответом, например китайские размеры, не перезапуская всю партию. Ручные правки, сделанные после первоначальной AI-обработки, в такой повторный запрос не входят.

Поля `brand`, `category` и `subcategory` внутри технической партии хранят канонические Rails UUID, но интерфейс всегда показывает их названия. При открытии старого снимка локальная таблица `catalog_id_mappings` используется как резервный источник подписей. Инструкции поставщика перед отправкой в AI автоматически очищаются от старых PocketBase ID и устаревших требований к формату ответа; справочники из текущего запуска всегда имеют приоритет.

AI запускается через OpenRouter или OpenAI-совместимый BYESU API. BYESU привязывает API-ключ к группе моделей, поэтому в server environment используются отдельные глобальные секреты: `BYESU_GEMINI_API_KEY` для группы Gemini Business, `BYESU_OPENAI_API_KEY` для группы OpenAI Codex, `BYESU_CLAUDE_API_KEY` для группы Claude и `BYESU_GROK_API_KEY` для группы Grok (xAI). AdminYeezy автоматически выбирает ключ по имени модели: `gemini-…` — Gemini Business, `claude-…` — Claude, `grok-…` — Grok, остальное — OpenAI Codex (`byesuModelGroup` в `lib/byesu.ts`). Ключи не хранятся в настройках поставщика. Старый `BYESU_API_KEY` поддерживается как временный fallback; его группу задаёт `BYESU_API_GROUP=gemini|openai|claude|grok` (по умолчанию `openai`). Как и остальные настройки, провайдер и модель фиксируются snapshot-ом конкретного запуска.

Для задач со сравнением по фотографиям (например, разбор фото поставщика в импорте David Studio) выбирайте `claude-sonnet-4-6` или `claude-opus-4-8`.

## Цены

С 27.10.2026 модалка `Правила цен` (строка списка выгрузок и меню «…» на странице выгрузки) содержит только одно свободное поле — инструкцию поставщика по ценам (`suppliers.price_ai_instructions`). Она сохраняется отдельным действием `saveSupplierPriceInstructionAction` и не трогает таблицу `supplier_price_rules`. Ранее созданные условные правила (на 27.10.2026 — 95 включённых у 11 поставщиков) в интерфейсе больше не показываются, но остаются в базе и по-прежнему применяются при AI-обработке по описанному ниже приоритету.

Если у товара есть `attributes.szwego_price` — цена из карточки товара поставщика в Szwego, в юанях (см. [выгрузки](./exports.md)), — она передаётся ИИ отдельной строкой промпта. Свободная инструкция может задавать расчёт от неё, например «Цена = szwego_price × 13 × 2.5, округлить до 100»: ИИ считает итоговую цену в рублях и возвращает её в `product.price`, а сервер принимает её как цену по инструкции (`price_source='ai_instruction'`), даже если такого числа нет в тексте инструкции. Если инструкция расчёт от `szwego_price` не задаёт, ИИ не должен брать её как цену. Арифметику выполняет ИИ, поэтому при первой обработке стоит выборочно сверить цены.

AI не придумывает цену. В карточке поставщика доступны условные правила по бренду, категории, подкатегории, модели, материалу, `size_class` (`small`, `medium`, `large`) и диапазонам ширины/высоты сумки. К правилу можно приложить до 9 фотографий и текстовую подсказку. Текстовые условия всех правил передаются AI, а визуальные эталоны предварительно отбрасываются только для правил, которым уже известные поля товара явно противоречат; подходящие эталоны передаются отдельным contact sheet и не смешиваются с фотографиями товара.

AI определяет `model_name`, `materials`, `bag_width_cm`, `bag_height_cm`, `size_class` и, при уверенном визуальном совпадении, `price_rule_key`. Сервер сохраняет подтверждённые габариты из `dimensions` или текста «Размер/尺寸»: тройка становится `Ш × В × Г см`, а для кошельков, картхолдеров и обложек допустима пара `Ш × В см`. Для категории «Сумки» ширина и высота дополнительно записываются в `bag_width_cm` и `bag_height_cm` до подбора цены; для «Аксессуаров» сохраняется только публичное поле `dimensions`. Номинальный размер модели не остаётся в `sizes`, а дописывается в название. Перед публикацией каталог также удаляет случайный `sizes` у сумок, поэтому он не создаёт варианты товара. `materials` входит в общую начальную схему, поэтому сохраняется и для сырого товара без категории, который AI позднее определит как «Сумки». После определения категории сервер сохраняет остальные зарегистрированные атрибуты сумок из ответа ИИ. Если цвет фурнитуры подтверждён явным текстом или описанием, сервер нормализует его в `hardware_color`. Сервер назначает цену детерминированно: точный визуальный эталон важнее правила модели и размеров, а они важнее резервного правила размерного класса. Количество фотографий в альбоме никогда не используется как условие цены.

В правилах поставщика можно выбрать `Кастомная формула AI`. В поле инструкции описывается, что искать в исходном тексте, например: «возьми максимальную цену из диапазона, умножь на 13 и 2.5». AI выбирает `price_rule_key`, а сервер извлекает суммы рядом с валютой/ценовым маркером, применяет `source_price` (`max` или `min`), множители и округление (`nearest`, `up`, `down`). Для `💰2399—4599`, множителей `13` и `2.5` и шага `1000` результатом будет `149000` при обычном округлении или `150000` при округлении вверх. Если цена в исходнике не найдена, кастомное правило не подставляет ноль и используется стандартная цена поставщика.

Приоритет:

1. ручная цена;
2. наиболее конкретное правило, затем больший числовой приоритет;
3. цена постпроцессора, если конкретный поставщик всё ещё её задаёт;
4. стандартная цена поставщика;
5. `0`.

При сохранении и перед каждым применением правила его условия `brand`, `category` и `subcategory` нормализуются через `catalog_id_mappings`. Поэтому правила, созданные со старым ID или с названием подкатегории, продолжают совпадать с текущими каноническими значениями Rails. Для фиксированной цены достаточно выбрать подкатегорию «Худи и толстовки», оставить тип расчёта «Фиксированная цена» и указать 24 000 ₽; цена применяется сервером после AI, даже если модель не вернула `price_rule_key`. При повторной AI-обработке уже установленная положительная или ручная цена сохраняется, а цена `0` считается неназначенной и может быть заполнена новым правилом.

## Перенос фотографий при публикации

Перед отправкой товаров в Rails каждое внешнее фото скачивается, преобразуется в WebP и сохраняется в настроенный S3 по пути `batches/{batch_id}/...`. Для SEO-перепубликации последней выгрузки имя строится как `{slug-товара}-{slug-фото}.webp`; для обычной публикации используется техническое имя партии. После `PutObject` наличие объекта проверяется через S3 API. Ссылки из собственного `S3_PUBLIC_DOMAIN` повторно не загружаются, кроме явной SEO-перегенерации.

Если хотя бы одно фото недоступно или не сохранилось в S3, публикация всей партии в Rails останавливается. Успешно перенесённые ссылки сохраняются в технической БД, поэтому следующий запуск повторяет только оставшиеся внешние фотографии. В Rails не передаются товары с внешними ссылками на фото.

Если Szwego-публикация содержит `videoUrl`, парсер сохраняет и обычные фотографии альбома, и техническую ссылку на видео. При публикации AdminYeezy скачивает ролик размером не более 150 МБ, через FFmpeg создаёт совместимый MP4 (H.264/AAC, максимум 1080 px, `faststart`) и WebP-постер, загружает оба файла в S3 и передаёт Rails поля `video_url` и `video_poster_url`. Для одинаковой исходной ссылки используется общий стабильный S3-ключ, поэтому один ролик не дублируется между товарами и повторными публикациями. Ошибка конкретного видео не скрывает фотографии и не останавливает остальные товары: она сохраняется как предупреждение публикации, а повторный запуск может снова перенести ролик. Тот же перенос (ключи `videos/{sha256}`, параметры FFmpeg и лимит 150 МБ) переиспользуется формой товара раздела «Каталог» через `rehostProductVideoAction`: ролик, уже перенесённый выгрузкой, при вставке той же ссылки в карточку товара повторно не кодируется.

Для каждого фото автоматически выполняются до трёх попыток скачивания, преобразования, загрузки и проверки. Фотографии одного товара переносятся с ограниченным параллелизмом: по умолчанию до четырёх одновременных задач, не более восьми; лимит можно задать через `MEDIA_UPLOAD_CONCURRENCY`. Повторное нажатие «Пуш» снова проверяет оставшиеся ссылки.

Редактор партии работает отдельной страницей `/admin/batches/{batch_id}`, а не временной модалкой. Прогресс публикации хранится как серверная операция и остаётся видимым после закрытия страницы. Кнопка остановки ставит запрос на корректное завершение между товарами; потерянная после перезапуска контейнера блокировка считается зависшей через пять минут и может быть безопасно сброшена или автоматически перехвачена повторным запуском.

До переноса фотографий AdminYeezy проверяет непустые `external_id` через Rails admin API пачками до 50 значений. Если точный `external_id` уже есть в основном каталоге, товар полностью пропускается: его фотографии не скачиваются, существующая карточка не обновляется. Новые товары импортируются пачками до 100 строк; размер по умолчанию равен 50 и может быть изменён через `RAILS_BATCH_PUBLISH_CHUNK_SIZE`. Эта настройка отделена от размера чанка других импортов. Rails выполняет импорт асинхронно в SolidQueue и сразу отвечает `202` с `import_batch_id`, поэтому публикация ждёт терминального статуса батча (`GET /api/v1/admin/import_batches/:id`), а не ответа на сам импорт: синхронный запрос упирался в rack-timeout 25 с и Rails отвечал `HTTP 500` на чанк из 50 товаров. Прежнее синхронное поведение осталось только как откат через `RAILS_IMPORT_ASYNC=0`. Партия получает статус `Запушено в БД` только после того, как все чанки дошли до статуса `processed`, а итоговое окно показывает реальное количество добавленных и пропущенных товаров. После каждого успешного Rails-чанка реестр `batch_publications` записывается одним bulk upsert; чанк с построчными ошибками в реестр не попадает, чтобы следующий запуск не счёл не созданный товар опубликованным.

В server-logs каждой публикации записываются тайминги фаз `lookup`, `media` и `publish`, чтобы после реальной выгрузки отделять сеть/S3 от работы Rails.

Кнопка публикации имеет два режима:

- `Добавить новые` пропускает уже существующие в Rails `external_id`;
- `Обновить и добавить` обновляет только существующие карточки, у которых изменился вычисленный publication payload, и добавляет новые.

Успешная публикация каждого Rails-чанка сразу фиксируется в `batch_publications`. Поэтому после сетевого сбоя повторный запуск продолжает работу без потери информации о уже созданных товарах. Для обычных новых выгрузок и обычного пуша старые объекты S3 не удаляются. Удаление неиспользуемых объектов выполняется только после успешной публикации явного запуска `Сгенерировать alt + slug` для самой последней выгрузки и только внутри префикса этой партии; общие фотографии сохраняются, чтобы не оборвать ссылки другой карточки.

## Дата публикации у поставщика

При создании новой альбомной выгрузки парсер сохраняет дату исходной публикации в `products.supplier_published_on` и во все JSONB-снимки партии. Сначала используются поля ответа Szwego, затем подпись товара и, если нужно, страница карточки. Относительные подписи (например, «17 минут назад») нормализуются в текущую московскую дату. AI, ручное редактирование, откат и публикация сохраняют это поле. В Rails оно передаётся отдельным `metadata.supplier_published_on`, в то время как `published_at` означает время пуша в каталог. Старые выгрузки не изменяются и показывают пустое значение.

## Целостность и восстановление

- Парсер создаёт партию, товары, сырой JSONB-снимок и связь с задачей одной транзакцией. Частично созданная партия откатывается целиком.
- Один поставщик может иметь только одну задачу парсинга со статусом `running`. Зависшая более 12 часов задача переводится в ошибку перед новым запуском.
- Для одной партии одновременно разрешена только одна операция: скрипт, AI, публикация, откат или удаление. Ручное редактирование во время обработки блокируется.
- Постобработка сохраняет товары, этап, снимок и запись истории одной транзакцией. Она всегда читает первый сырой снимок, поэтому повторный запуск не уничтожает китайский исходник.
- Просмотр снимка является только чтением и никогда не восстанавливает или не заменяет текущие товары автоматически.
- Официальные снимки `Сырой товар` и `Обработан скриптом` сохраняются. Для повторных технических AI-снимков хранится не более 10 последних снимков каждого типа.
- `batch_id` и непустой `external_id` обязательны для каждого технического товара; завершённая scraping-задача обязана ссылаться на существующую партию.
- При публикации перенесённые S3-ссылки фиксируются после каждого товара. Повторный запуск проверяет уже загруженные объекты и продолжает с оставшихся фотографий.

## Предложения справочников

Для трёх поставщиков Chromoff AI дополнительно получает отдельный справочник
активных категорий Chromoff. Выбранный `chromoff_category_id` сохраняется в
metadata товара и используется при публикации в `ChromoffListing`; общая
категория YeezyUnique при этом не подменяется. Низкая уверенность (ниже 0.75)
помечает listing как `needs_review` и не публикует его автоматически.

После AI отдельный экран показывает предложения цветовых семейств. Для цветового семейства отображаются модель, найденные цвета, количество товаров, первые фотографии и габариты; служебный JSON свёрнут в блоке `Технические данные`. AI выбирает подкатегории и атрибуты только из существующих справочников и не предлагает новые.

В окне предложений доступны массовые действия `Принять всё` и `Отклонить всё`. Отклонение помечает все ожидающие предложения текущей партии как отклонённые одной операцией и не меняет товары.

В настройках поставщика в группе `Постоянные настройки AI-обработки → Предлагать` можно отдельно включить предложения новых подкатегорий и атрибутов. Оба переключателя выключены по умолчанию: AI по-прежнему выбирает существующие значения, но новые предложения не создаются.

В фильтрах товаров партии доступен режим `С видео`/`Без видео`. Видео определяется по исходной или уже перенесённой ссылке `video_url` в атрибутах товара.

## Библиотека шаблонов замеров

Внешние скриншоты размерных сеток не смешиваются с альбомами поставщика. На
странице `/admin/measurement-templates` оператор один раз загружает скриншот,
может распознать его через настроенный OpenRouter/BYESU AI, проверяет
структурированную таблицу (размеры, колонки, единицы и заметку) и
сохраняет её по типу одежды и конкретному поставщику. В карточке выгрузки
видны только шаблоны поставщика текущей партии. Во время полной AI-обработки
система автоматически применяет единственный шаблон подходящего типа к товару
того же поставщика: штаны, шорты, худи, зип-худи или вафельный лонгслив.
Тип определяется по новому названию, H1 и подкатегории товара, а не по
описанию. При нескольких шаблонах одного типа или неоднозначном товаре замеры
не меняются. ИИ-таблица замеров, прочитанная непосредственно с фото товара,
имеет приоритет. Ручное применение заменяет только `attributes.measurements`,
не меняя описание, изображения и видео; строки таблицы одновременно записываются
в `attributes.sizes`, чтобы основной сайт построил варианты/табы `S`, `M`, `L`,
`XL` и т. п. Существующие размеры не затираются, а объединяются с размерами
шаблона.

В основном каталоге тот же шаблон можно выбрать в панели массовых действий и
назначить отмеченным опубликованным товарам. Операция сохраняет остальные
`catalog_attributes` каждого товара и добавляет таблицу замеров и её размеры.

При распознавании AI получает не уменьшенную плитку контакт-листа, а
подготовленный сервером фрагмент исходного скриншота: белые поля обрезаются,
сама таблица увеличивается и передаётся непосредственно в запросе к модели.
Затем второй запрос с тем же изображением независимо сверяет размеры, форму
сетки и значения ячеек; переводы китайских названий параметров могут
отличаться и не считаются расхождением. Если данные сетки не совпадают,
таблица не применяется. Он переносит в ячейки только точные значения внутри
сетки. Ответы OpenAI-совместимых провайдеров приводятся к одному текстовому
потоку даже если `message.content` пришёл массивом, после чего из markdown или
поясняющего текста извлекается JSON и нормализуется к форме
`{unit,columns,rows,note}`.
Примечания вроде «ручное измерение, допустима погрешность 1–2 см» сохраняются
только в поле заметки к таблице: значение `86` не превращается в диапазон
`86–90`. Если AI не может уверенно прочитать сетку, он возвращает ошибку и не
подставляет типовую размерную таблицу; оператор может загрузить более чёткий
скриншот или заполнить поля вручную.

В карточке товара выгрузки цветовую семью можно исправить вручную: создать семью из выбранных товаров, добавить товары в текущую, привязать товар к уже существующей семье или отвязать его. При создании обязательно указывается название; оно хранится в `variant_group_name` вместе со стабильным `variant_group_key` и показывается в заголовке семейства. В просмотре выгрузки кнопка `Семейные группы` открывает список всех семей с названием и числом товаров; при открытии семьи видны её карточки. Массовый выбор также позволяет создать новую именованную семью из выбранных товаров или добавить их в существующую.

При одобрении:

- цветовое семейство получает общий стабильный `variant_group_key`.

### Единые поля цветовой семьи

Цветовая семья — один товар одного поставщика в разных цветах. Отличаться
могут только цвет и то, что от него зависит: цветовая часть названия и
описания, фото, alt, slug и наличие. Бренд, категория, подкатегория, пол, цена,
размерный ряд и размерная сетка обязаны совпадать. Правила реализует общий
модуль [scripts/lib/color-family-alignment.js](../scripts/lib/color-family-alignment.js),
его используют AI-конвейер и публикация.

**Выравнивание после AI-прохода.** ИИ обрабатывает каждую карточку отдельно и
может по-разному классифицировать цвета одного альбома. Поэтому после
завершения любого AI-запуска, кроме `variants` и `media_seo`, сервер выравнивает семьи, в которые входит хотя бы один
обработанный в этом запуске товар. Семья, где ещё есть необработанные ИИ товары,
пропускается. Расхождение в общих полях — шум ИИ, а не повод распустить семью,
собранную постобработкой по альбому:

- бренд, пол, пара «категория + подкатегория» и `model_name` берутся по
  большинству цветов, при равенстве — у якоря (первый цвет альбома
  `album_colour_index`, затем `source_position`);
- `materials` не выравнивается: у поставщика 28 в одной семье бывают кожаные и
  замшевые ботинки, и большинство переписало бы материал реального изделия
  (так было на выгрузке `69c945ba` у 275 товаров до исправления; материалы там
  восстановлены из ответа ИИ). Разные материалы разделяет семейный AI-шаг ниже;
- цена берётся по большинству положительных цен; если у кого-то из цветов цена
  ручная, общая цена выбирается только среди ручных;
- `hardware_color`, `dimensions`, `bag_width_cm`, `bag_height_cm` дописываются
  цветам, у которых их нет;
- размерная сетка: если таблица замеров найдена хотя бы у одного цвета, она
  вместе с `sizes` и `size_recommendation` записывается всем цветам. Фото самой
  сетки в публичную галерею не переносится: AI всё равно убирает его оттуда.
  Таблицы сравниваются по содержимому строк размеров, а не по порядку колонок,
  подписям и ключам: ИИ называет одну колонку то `insole_length`, то `insole`.
  Числа сравниваются как числа (`27.0` = `27`), значение в 10 раз больше
  считается той же ячейкой в миллиметрах (`268` при единице «см» = `26.8`),
  метки `M(48)` и `M`, `2XL` и `XXL` — один размер. Если таблица отличается от
  основной не более чем в 20% ячеек (включая лишнюю или пропущенную строку
  размера), это та же сетка, прочитанная с ошибкой, и всем цветам записывается
  основная: самая частая, при равенстве — с меньшими числами, затем по якорю.
  Пропущенная колонка или строка не делает сетку другой: если каждая ячейка
  одной таблицы есть в другой, это та же сетка, и всем записывается более полная.
  Если у одного цвета совсем другая таблица, а у большинства цветов одна и та же,
  всем записывается таблица большинства: на выгрузке `69c945ba` у ST2545 один
  цвет прочитал длину стопы вместо длины стельки (на 2 см меньше). Конфликтом
  остаются только разные сетки без большинства, например один цвет против одного.
  Так же считается одной сеткой таблица с общим `size_chart_source_id`.
  Проверено на выгрузке `69c945ba` (LP, Zegna, BC): из 23 семей с «разной
  сеткой» настоящей оказалась одна, остальные — разное прочтение одной таблицы.

**Одна картинка сетки — одно прочтение.** ИИ читает сетку в карточке каждого
цвета отдельно, а постобработка копирует одну и ту же картинку сетки во все
цвета семьи. На `b2446b7d` одну картинку четыре цвета поло прочитали тремя
способами (обхват груди 102 и полуобхват 51), а два цвета брюк — с разными
колонками. Поэтому перед выравниванием (после AI-запуска и по кнопке
`Выровнять семьи`) сервер ([lib/family-size-charts.ts](../lib/family-size-charts.ts))
берёт из ответа ИИ на каждую карточку кадр, который ИИ распознал как сетку,
и записывает его в `attributes.size_chart_photo_urls` (в Rails не уходит).
Если одна картинка есть у нескольких цветов и прочтения различаются, картинка
распознаётся заново тем же способом, что в библиотеке шаблонов замеров
([lib/measurement-recognition.ts](../lib/measurement-recognition.ts): обрезка,
увеличение и два независимых прочтения), и таблица с размерным рядом
записывается всем этим цветам. Если повторное распознавание не удалось, берётся
самое частое и полное из прочтений. Сетки с разных картинок поставщика не
конфликт: каждый цвет сохраняет свою таблицу и свой размерный ряд.

Что нельзя решить автоматически, записывается в `ai_error` каждого затронутого
товара с префиксом `Цветовая семья:` и видно красной плашкой в карточке:
пустой цвет, одинаковое название у двух цветов (даёт одинаковые H1 и title),
два разных значения физического признака, две разные ручные цены и разные
размерные сетки (например, таблица только от брюк комплекта или другой крой).
Совпадение `attributes.colors` ошибкой не считается: там часто базовый цвет, и
«Тёмно-серый» и «Светло-серый» оба записаны как «Серый». Следующее успешное выравнивание снимает эту пометку; ошибки самого
AI-ответа шаг не перезаписывает. Итог запуска пишется в лог сервера строкой
`[color-family-alignment]`.

**Кнопка `Выровнять семьи`.** В просмотре выгрузки рядом с `Семейные группы`
кнопка выполняет то же выравнивание для всех семей партии без обращения к ИИ —
так исправляются уже обработанные и опубликованные выгрузки без платного
перезапуска. Затем окно показывает те же конфликты, что остановят публикацию:
по каждой семье — расхождения и товары, по клику открывается карточка. Семьи,
где ещё есть необработанные ИИ товары, не выравниваются и не показываются.
Кнопка недоступна при несохранённых правках и во время другой операции с
выгрузкой (AI, публикация, скрипт).

**Одобрение предложения ИИ.** Семью, которую предложил ИИ, сервер не
исправляет. Одобрение отклоняется с перечнем расхождений, если у выбранных
товаров разные бренд, пол, категория или подкатегория, цена, физические
признаки или разные размерные сетки. После успешного одобрения семья
выравнивается тем же шагом, поэтому сетка одного цвета переносится на остальные.
Ручное создание семьи в карточке товара не проверяется.

**Публикация.** Перед переносом фотографий `pushBatchToCatalog` проверяет каждую
семью партии из двух и более товаров строго, без исправлений: совпадают бренд,
пол, категория и подкатегория, цена, физические признаки и `sizes` (у сумок
`sizes` не учитывается: публикация его удаляет); сетка есть у всех цветов или
ни у одного и это одна сетка (ошибка прочтения нескольких ячеек допустима);
цвет указан, названия разные. При расхождении публикация всей партии
останавливается с названием семьи и `external_id` товаров. Исправьте товары вручную либо
перезапустите ИИ для нужных карточек: выравнивание выполнится по завершении
запуска.

### Согласование названий семей (режим `family_names`)

ИИ обрабатывает каждый цвет отдельно и не видит остальных цветов семьи.
Поэтому основа названия расходится («вязаный» и «трикотажный» кардиган,
«ботинки» и «полуботинки»), а два близких оттенка получают одно название и
одинаковый H1. На выгрузке `69c945ba` так получилась 21 семья с одинаковыми
названиями; у поставщика нет названий цветов, только «Палитра: 12 оттенков».

Семейный шаг — отдельный AI-запуск с режимом `family_names`: один vision-запрос
на семью ([lib/batch-ai-family-naming.ts](../lib/batch-ai-family-naming.ts)).
ИИ получает contact sheet из главного фото каждого цвета, текущие названия,
цвета и материалы и возвращает:

- `base_name` — общую основу названия без бренда и цвета, одинаковую слово в
  слово у всех цветов, и её английский вариант;
- для каждого цвета точный оттенок, уникальный внутри семьи («Коричневый» и
  «Тёмно-коричневый»), `base_color` для фильтра и полное название `name`/`name_en`
  с согласованным прилагательным цвета;
- разбиение на группы, если на фото явно разный материал верха (кожа и замша)
  или тип изделия (ботинки и полуботинки).

Сервер проверяет ответ: каждый товар ровно один раз, `name` содержит основу
группы, названия в группе разные (кроме явных дублей `duplicate_of_index` —
повторной публикации того же оттенка). При ошибке модель получает один
повторный запрос с причиной отказа, затем запрос семьи помечается ошибкой
запуска, а товары семьи не меняются.

Если ИИ по главному фото счёл два цвета одним оттенком, выполняется ещё один
запрос только по этим товарам: до четырёх фото каждого. Модель ищет различие в
оттенке при другом освещении, подошве, подкладке, меху, нитках или фурнитуре и
обязана дать разные названия: поставщик выкладывает разные цвета палитры, а не
повторы (на `69c945ba` у KTH001 и LP099 ИИ дважды объявлял дублем цвета, которые
оператор видит как разные оттенки). Дублей после повторной проверки не бывает.
Если её ответ не проходит проверку, сохраняется первый ответ.

Повторный запуск `Согласовать названия семей` берёт только несогласованные
семьи: где семейный шаг ещё не завершался после последней AI-обработки цвета
или где у цветов остались одинаковые названия. Временный отказ провайдера
(«文本服务繁忙，请稍后重试», «service busy») повторяется автоматически, как и
другие временные ошибки. Применение пишет `name`, `h1`,
`attributes.colors`, `attributes.base_colors` и `translations.en.name`
(статус `machine`). Группа с первым цветом альбома сохраняет ключ семьи,
остальные группы получают новые ключи и имя `«семья» · материал`, группа из
одного товара перестаёт быть семьёй. Описание, slug и фото не меняются.

Запуск автоматический:

- после любого AI-запуска, который довёл выгрузку до конца (полная обработка,
  повтор упавших карточек, обработка выбранных), если в ней есть
  несогласованные семьи; затем, при включённой настройке поиска семей среди
  соседних карточек, — `variants`;
- после закрытия окна `Предложения ИИ`, если в нём одобрена хотя бы одна
  цветовая семья. Запуск один на всё окно, а не на каждое одобрение: иначе идущий
  запуск блокировал бы следующие одобрения и `Принять всё`.

Вручную: меню AI в выгрузке → `Согласовать названия семей`.
По завершении семьи выравниваются, как после любого AI-запуска.

H1 равен `name`, title и meta description формирует Rails.

```bash
npm run db:migrate:scraping
```

Полная миграция создаёт папки, снимки, AI-очередь, предложения, ценовые правила, таблицу бывшего справочника моделей Chanel, библиотеку шаблонов замеров, worker state, блокировки операций и реестр публикаций; она также добавляет ограничения целостности и удаляет таблицы `scraping_v2_*`.
