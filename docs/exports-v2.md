# Выгрузка 2.0

`/admin/exports-v2` — отдельный экспериментальный контур для перехода от CSV-строк к исходным альбомам и товарам в PostgreSQL. Старая выгрузка `/admin/batches` не изменяется и остаётся рабочим вариантом отката.

## Текущий статус

Сейчас реализован безопасный DB-native этап:

- исторический сырой CSV можно один раз импортировать в V2 для сравнения со старыми скриптами;
- отдельный `SzwegoParserV2.py` передаёт альбомы потоком JSONL и сохраняет их сразу в PostgreSQL, без промежуточного CSV;
- повторный запуск того же поставщика продолжает тот же активный V2-набор: новый `external_id` добавляется, неизменившийся пропускается, изменившийся получает новую ревизию;
- каждый исходный альбом хранится отдельно, а история изменившегося содержимого сохраняется;
- несколько альбомов можно вручную объединить в один черновик товара;
- каждому альбому назначается роль;
- размеченную группу можно сохранить как пример для будущих правил и AI;
- production-публикация из V2 заблокирована и в интерфейсе, и ограничением базы.

V1 и `SzwegoParser.py` не изменены. Новый парсер запускается только из `/admin/exports-v2`, не создаёт строки каталога, batch и CSV и не применяет старые фильтры `min_photos`/`min_desc_len`. Поэтому сырые фотографии, подпись и полный ответ Szwego сохраняются до разметки.

## Роли исходных альбомов

| Роль | Медиа в карточке | Текст для AI | Назначение |
| --- | ---: | ---: | --- |
| Основные медиа | да, первыми | нет | Главные фото и видео без использования подписи альбома |
| На модели | да, с лимитом | нет | Кадры товара на человеке; лимит задаётся у поставщика, по умолчанию 5 |
| Медиа + текст | да | да | Полезны и фото/видео, и подпись альбома |
| Дополнительные медиа | да | нет | Детальные фото и видео без использования подписи |
| Только текст | нет | да | Описание или характеристики из соседнего альбома |
| Размеры / OCR | нет | да | Таблица размеров и замеров; изображение не публикуется |
| Сравнение / реклама | нет | нет | Сравнение с оригиналом, китайская рекламная плашка и похожий мусор |
| Игнорировать | нет | нет | Альбом не относится к товару |

Количество фотографий само по себе не определяет роль. Один кадр может быть полезной таблицей размеров, а альбом с несколькими кадрами — рекламным сравнением.

Альбом открывается из сетки и из собранного товара. Для изображений Szwego интерфейс использует серверные преобразования `imageMogr2`: миниатюры `420×420 WebP`, просмотр — до `1280×1280 WebP`. Исходный URL остаётся в БД без изменений. Видео хранится как тип медиа внутри альбома, а не как отдельная роль: оно попадает в будущую карточку только у ролей, разрешающих медиа.

В исходной БД всегда остаются все фото и видео. Лимит «На модели» влияет только на будущую галерею товара. Итоговый порядок детерминирован: `Основные медиа → Медиа + текст → На модели → Дополнительные медиа`. Внутри каждой роли сохраняются порядок альбомов в ленте поставщика и порядок медиа внутри альбома. Каждому элементу назначается собственный `sort_order`.

## Сохранность исходных данных

Исходный альбом сохраняет:

- стабильный `external_id`;
- исходный порядок;
- исходные название и описание;
- полный список фотографий;
- типы медиа, ссылки на видео и их кадры-превью;
- полный `raw_payload`;
- SHA-256 `content_hash`.

Разметка не переносит и не удаляет исходные данные. Она только связывает альбом с черновиком товара и задаёт, что именно разрешено использовать. Поэтому старые скрипты можно сравнивать с V2 без риска потерять фотографии или описание.

## Таблицы

- `scraping_v2_runs` — тестовый запуск поставщика;
- `scraping_v2_scrape_passes` — отдельные снимки ленты поставщика при каждом запуске;
- `scraping_v2_albums` — текущее состояние исходных альбомов;
- `scraping_v2_album_observations` — позиция альбома, страница и номер на странице в конкретном снимке;
- `scraping_v2_album_revisions` — версии альбома при изменении текста, фото или другого содержимого;
- `scraping_v2_product_drafts` — собранные товары;
- `scraping_v2_draft_albums` — связь товара с альбомами и их роли;
- `scraping_v2_training_examples` — подтверждённые оператором примеры.

Миграция:

```bash
npm run db:migrate:scraping-v2
```

Парсер использует интерпретатор из `PYTHON_PATH` (по умолчанию `python`) и зависимости из `requirements.txt`. На Windows важно, чтобы `PYTHON_PATH` указывал на реальный `python.exe`, а не на Microsoft Store alias.

Ограничение `scraping_v2_runs_production_push_disabled` не позволяет установить `production_push_enabled=true`. У V2 также пока нет server action публикации в Rails.

## Пилотный порядок работы

1. Открыть `/admin/exports-v2`.
2. Выбрать поставщика в блоке «Новая DB-native выгрузка» и запустить получение альбомов. Исторический CSV нужен только для сравнения V1 и V2.
3. Выделить альбомы одного товара и нажать «Это один товар».
4. Для каждого источника выбрать роль.
5. Проверить план галереи, лимит «На модели», текстовые источники и OCR-таблицы.
6. Сохранить подтверждённую группу как пример поставщика.

Первые поставщики для проверки: Chanel Сумки, Zimmermann Одежда и Женская одежда 4. Их старые скрипты используют разные схемы объединения, поэтому они хорошо покрывают основные риски.

## Правила дозагрузки

- Активный DB-native запуск один на поставщика.
- Ключ альбома внутри него — `external_id`; повторно полученный альбом не создаёт дубль.
- `content_hash` считается по `external_id`, названию, описанию и исходным URL фото/видео.
- Новая версия содержимого сохраняется в `scraping_v2_album_revisions`, после чего в `scraping_v2_albums` обновляется текущее состояние.
- Порядок не перезаписывается одним глобальным номером: каждый проход сохраняет собственную последовательность в `scraping_v2_album_observations`. Поэтому дозагрузка новых верхних альбомов не ломает старые обучающие примеры.
- Старые альбомы не удаляются, потому что поставщики сохраняют свою историю и обычная дозагрузка не является достоверным снимком наличия.
- `batch_id` появится только на будущей стадии публикации товаров. Для дедупликации источника используется `external_id`; для удаления опубликованной партии должен использоваться отдельный publication batch.

## Порядок и обучающие примеры

Новый пример имеет `version: 3` и привязан к конкретному завершённому проходу парсера. В нём сохраняются:

- порядок выбранных альбомов в ленте поставщика;
- страница и позиция на странице;
- расстояние и количество промежуточных альбомов между частями товара;
- до четырёх соседних альбомов с каждой стороны;
- все промежуточные альбомы, если общий фрагмент не длиннее 40 позиций;
- метка `SELECTED`, `OTHER_PRODUCT` или `UNASSIGNED_CONTEXT`;
- роль выбранного альбома, текст, количество фото/медиа, наличие видео и ссылка на первую миниатюру.
- рассчитанный `media_plan` с финальным `sort_order` и применённым лимитом «На модели».

Это покрывает последовательные правила старых скриптов: `i → i+1`, «заголовок → следующие детали», пропуск служебного альбома и границу между соседними товарами. Исторические V1-выгрузки используют порядок строк CSV как резервный порядок. Старые примеры остаются в БД, но будущая AI-группировка должна предпочитать актуальную версию 3.

## Экономная визуальная обработка AI

AI не должен получать все полноразмерные фотографии сразу. План обработки двухступенчатый:

1. Сформировать contact sheet из 30–50 миниатюр первых кадров. На каждой плитке показать позицию альбома, количество фотографий и признак видео. Вместе передать короткие подписи и сохранённый порядок.
2. AI предлагает группы и помечает сомнительные места. Только для них открыть 1–3 дополнительных кадра, полный текст или OCR таблицы размеров.

Плитка хорошо определяет границы товаров и мусорные альбомы с гораздо меньшими затратами. Она не заменяет второй проход: по одному первому кадру нельзя надёжно отличить похожие модели, прочитать мелкую размерную таблицу или решить, какие детальные фотографии относятся к товару.

Проверка живой ленты Szwego показала, что для группировки полезны не только изображения: `goods_id`, позиция, число медиа, фото/видео, подпись, внутреннее название в блоке «Подробности», время публикации и временные метки в именах CDN-файлов. Например, соседние альбомы на 9 и 4 фото и следующий видеоальбом имели одно внутреннее название `cf23` и одно время публикации. Эти сигналы нужно объединять с разметкой оператора; один только шаблон количества фото не является достаточным правилом.

## Следующий этап

Перед включением автоматического объединения нужно:

1. Построить предложения группировки на правилах старого скрипта и сохранённых примерах, но оставлять сомнительные группы на ручную проверку.
2. Передавать AI только разрешённые роли: медиа из `PRIMARY_MEDIA`/`MEDIA_WITH_TEXT`/`ON_MODEL`/`EXTRA_MEDIA`, текст из `MEDIA_WITH_TEXT`/`TEXT_ONLY`, OCR из `SIZE_CHART`.
3. Рассчитывать цену по настройкам поставщика и категории; не извлекать цену из исходного альбома.
4. Добавить экран сравнения результата V1 и V2: количество товаров, потерянные альбомы, фотографии и текстовые источники.
5. Только после приёмки нескольких поставщиков отдельно проектировать публикацию и удаление опубликованной партии.

До этой приёмки V1 остаётся основным production-процессом.

## Сколько нужно примеров

Сохранение примера пока не запускает обучение модели. Это размеченные данные для будущего поиска похожих случаев и few-shot подсказок.

Практический ориентир на одного поставщика:

- 20–30 качественных групп — можно включать предложения AI только с ручным подтверждением;
- 50–100 разнообразных групп — обычно достаточно для устойчивых повторяющихся схем поставщика;
- отдельно 10–20 сложных отрицательных примеров: реклама, сравнение, одиночный мусор, таблица размеров и похожие, но разные товары.

В один запрос AI не нужно передавать все примеры. Следующий этап должен выбирать 5–10 наиболее похожих примеров, а качество измерять на отдельной контрольной выборке, которая не использовалась как подсказка.
