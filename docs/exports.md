# Раздел «Выгрузки»

Раздел `/admin/batches` предназначен для работы с партиями товаров:

Полный новый AI-конвейер, папки, снимки, правила цен и локальный Cockpit worker описаны в [AI-обработке китайских товаров](./batch-ai-workflow.md).

1. запуск выгрузки поставщика;
2. просмотр сырого снимка товаров;
3. постобработка скриптом;
4. AI-обработка;
5. ручная проверка и редактирование;
6. публикация в Rails-каталог.

## Источники данных

Техническая база `yeezy_scraping` хранит несколько связанных сущностей:

- `scraping_batches` — логическая партия;
- `scraping_tasks` — запись об отдельном этапе обработки;
- `batch_snapshots` — неизменяемый JSONB-снимок этапа;
- `products` — текущее редактируемое состояние товара в партии.

### Теги и группы Szwego

Szwego фильтрует альбомный API по числовому ID, а не по названию тега. В
настройках сохранённого поставщика в блоке «Теги групп и подгрупп» нажмите
«Обновить из Szwego»: AdminYeezy использует сохранённый Cookie и один запрос к
`album/personal/image`, получает дерево «группа категорий → альбомы» с их ID и
добавляет его в список без удаления уже введённых строк. Запрос не обходит
товары альбома и ограничен 15 секундами. Проверьте результат и сохраните
поставщика; затем при запуске выгрузки выбирайте тег по его названию — в API
будет передан соответствующий ID.

У каждой строки есть флажок: включённые категории и альбомы доступны в окне
запуска выгрузки, выключенные остаются в настройках, но не предлагаются для
выгрузки. Впервые обнаруженные строки и старые записи без сохранённого статуса
выключены до явного выбора оператора — так новая синхронизация не может
случайно запустить выгрузку всего альбома.

Если Szwego возвращает ошибку с истёкшей сессией, обновите Cookie поставщика.
Эта операция не открывает браузерную ссылку альбома и не изменяет данные
поставщика до явного сохранения формы.

Для новых альбомных выгрузок `products.supplier_published_on` хранит дату, когда товар был выложен у поставщика. Парсер берёт дату из полей и карточки альбома; относительные подписи вроде «17 минут назад» считаются текущей датой по Москве. Если отдельное поле даты отсутствует, импорт и AI-нормализация используют `szwego_timestamp` как запасной источник даты. Это системное поле, а не дополнительный JSON-атрибут: AI не удаляет его из товара и не добавляет в `attributes`.

В карточке выгрузки публичные характеристики редактируются отдельно от технической информации. В техническом блоке только для чтения находятся дата/время источника, теги Szwego, ссылки на исходное видео, режим парсинга и прочие служебные значения; они не публикуются как характеристики товара. H1 и SEO-поля в карточке выгрузки и стандартном CSV не показываются: Rails формирует их из финальных фактов товара при публикации.

История выгрузок группирует задачи по `batch_id`. Старые задачи без партии показываются как отдельные синтетические записи.

В раскрытой партии этапы показаны компактным путём `Сырой товар → Скрипт → ИИ → Опубликовано`. Этап `Скрипт` показывается только если у поставщика настроен post-process-скрипт. Начало и конец периода находятся в одной ячейке; если дата окончания не задана, отображается `Весь период`. Текущий этап можно редактировать, старые снимки открываются только для просмотра; восстановление снимка выполняется отдельной кнопкой `Восстановить версию…`.

В меню троеточия партии кнопка `Точечная настройка ИИ` открывает параметры цветовой семьи, разделения цветов альбома, первого фото и исключения альбомов только с моделями. Те же параметры можно применить к тесту первых 10 товаров или к полной обработке; отдельного третьего прохода по файлу нет.

## Где редактировать товары

В истории нажмите нужный этап партии. Полноэкранная страница `/admin/batches/{batch_id}` открывает текущую версию товаров из `scraping.products`, а параметр `?snapshot={snapshot_id}` — выбранный неизменяемый снимок. Поэтому сырой, обработанный скриптом и AI-этапы не подменяют друг друга при открытии.

Редактор поддерживает:

- название;
- описание;
- цену;
- бренд;
- категорию;
- подкатегорию;
- фотографии, в том числе добавление внешней ссылки `http://`/`https://` прямо
  в галерею товара;
- дополнительные атрибуты.
- видео товара: оно отображается отдельным плеером с poster, если в исходных атрибутах есть ссылка поставщика или уже загруженная S3-ссылка.

В режиме карточек плотность сетки регулируется ползунком от 4 до 10 карточек в ряд. Семейные группы цветовых вариантов открываются отдельной кнопкой: сначала показывается список семей с названием и числом товаров, затем — карточки выбранной семьи. При создании новой семьи нужно указать её название; оно также показывается внутри карточки товара. В массовых действиях выбранные товары можно объединить в новую именованную семью или добавить в существующую. Для последовательного выбора диапазона используется Shift: обычным кликом выбрать начало, затем кликнуть с Shift по конечной карточке.

В массовой панели выбранным товарам можно одновременно назначить шаблон размеров поставщика. Применение сохраняет остальные атрибуты, записывает таблицу в `attributes.measurements` и объединяет размеры строк шаблона с `attributes.sizes`.

В панели фильтров доступен единый поиск по названию, описанию и `external_id`. Значения фильтров и их счётчики пересчитываются по текущему поиску и другим выбранным условиям; недоступные значения исчезают из списка. Гендеры отображаются нормальными подписями «Мужское», «Женское» и «Унисекс». Панель сделана компактной: на широком экране селекты занимают общую flex-сетку и имеют высоту 36 px, на узком экране автоматически переносятся на следующие строки.

Изменения в партии сохраняются в базу. Для одиночных полей используется короткая задержка перед запросом, поэтому каждое нажатие клавиши не создает отдельный SQL-запрос.

## Атрибуты товаров

Атрибуты хранятся в поле `products.attributes` типа JSONB. Старые поля товара не меняются.

Пример:

```json
{
  "color": "black",
  "material": ["cotton", "elastane"],
  "model": "M60895",
  "model_name": "Samba"
}
```

Правила:

- ключ должен начинаться с буквы или цифры;
- допустимы буквы, цифры, `.`, `_`, `-`;
- длина ключа — не более 64 символов;
- значение может быть строкой, числом, boolean, `null` или массивом таких значений;
- системные поля (`name`, `price`, `photos`, `category` и т. п.) нельзя записать как атрибут.

Неизвестные поля JSON сохраняются как атрибуты. При ручном экспорте атрибуты записываются отдельной колонкой `attributes` с JSON-значением.

## Совместимость с CSV

CSV остаётся только ручным форматом импорта и экспорта. Автоматический парсер, post-process и AI работают с JSON/JSONB и не создают `task_*.csv` или `task_custom_*.csv`.

Для ручного экспорта без атрибутов формат не меняется:

```text
external_id;name;description;price;status;brand;category;subcategory;gender;photos;ai_processed
```

Колонка `attributes` добавляется только когда в товарах действительно есть дополнительные атрибуты.

Важно: CSV-парсер старается сохранять старые правила разделителей, кавычек и кодировок. Не следует вручную исправлять строки путем добавления разделителей внутрь неэкранированного описания. Для сложных машинных обменов предпочтителен JSONL или прямое сохранение партии в БД.

## Проверка перед публикацией

Перед публикацией выполняются проверки:

- дубли `external_id` — ошибка;
- отсутствие `external_id` — ошибка: такой товар нельзя безопасно повторно публиковать или обновлять;
- пустое название — предупреждение;
- отрицательная или некорректная цена — ошибка;
- некорректный ключ атрибута — ошибка.

Ошибки останавливают публикацию. Предупреждения показываются оператору, но не блокируют процесс.

Для партий с атрибутами используется batch-путь публикации, чтобы дополнительные данные не потерялись на старом прямом импорте.

Перед production-публикацией партия с атрибутами передаёт колонку `attributes` с JSON-объектом. Rails importer сохраняет её в `products.catalog_attributes`; админка добавляет колонку только для партий, где атрибуты заполнены. Публикация старых партий остаётся без изменений.

При публикации существующего товара в Rails также передаётся `variant_group_key`. Поэтому одобренная цветовая семья сохраняется не только при создании товара, но и при повторном обновлении; в основном каталоге админки такие товары отображаются с числом и названиями цветов семьи.

Видео с одинаковой исходной ссылкой получают общий стабильный S3-ключ `videos/{sha256}.mp4`; повторная публикация использует уже загруженный файл и не создаёт копию для каждого товара.

## Порядок работы оператора

1. Запустить выгрузку поставщика.
2. Дождаться статуса `Сырой товар`.
3. При необходимости выполнить постобработку.
4. Запустить AI-обработку.
5. Открыть текущую версию партии из БД.
6. При необходимости нажать `Найти варианты`: отдельный текстовый AI-проход проверит обработанные товары на цветовые варианты, не меняя карточки и не отправляя фотографии.
7. Проверить товары, предложения ИИ и атрибуты.
8. Одобрить нужные цветовые семейства: только после одобрения товары получают общий `variant_group_key`.
9. Сохранить ручные изменения.
10. AI автоматически генерирует alt и slug фотографий в рамках текущего процесса. В блоке очереди доступны `Показать ошибки` и `Повторить ошибки`: повторная попытка создаётся только для неуспешных товаров последнего запуска.
11. Исправить ошибки валидации.
12. Нажать `Обновить каталог`, чтобы передать alt и slug в Rails и перевыложить фото в WebP с именем `{slug-товара}-{slug-фото}.webp`. Для обычных новых выгрузок фото также сразу переводятся в WebP; удаление старых объектов S3 выполняется только после успешного SEO-запуска для последней выгрузки.

Публикация запускается только со страницы партии. Её этап и счётчик (`Проверка`, `Фото`, `Публикация`) хранятся в технической БД и восстанавливаются после обновления страницы или повторного входа. Живую операцию можно остановить; если процесс был убит деплоем и не обновлялся более пяти минут, интерфейс предлагает сбросить зависшую блокировку и безопасно повторить идемпотентную публикацию.

В истории текущий этап партии помечен как «Текущая редактируемая версия» и открывается напрямую из JSONB: ручные изменения сохраняются в `products`. Более ранние этапы остаются неизменяемыми снимками только для просмотра, чтобы редактирование сырого снимка случайно не перезаписало уже обработанную партию.

## Удаление

Действия разделены:

- `Удалить этап из админки` — удалить конкретную запись этапа и её файловый артефакт;
- `Удалить историю выгрузки` — скрыть партию из истории и удалить связанные записи, не удаляя товары из Rails;
- `Удалить локальную партию` — удалить товары из технической БД выгрузок, сохранив историю; основной каталог всегда не затрагивается;
- `Удалить из основного каталога` — отдельное действие только для опубликованной партии. Локальные товары и история при этом остаются. Действие доступно и для старых партий со стадией `PUSHED`, у которых ещё нет записей в `batch_publications`.

Для опубликованной партии локальное удаление сохраняет `batch_publications` и S3-медиа, пока каталог не очищен: Rails всё ещё может ссылаться на эти объекты. Непушенная партия может удаляться локально вместе со своими медиа без риска для основного каталога. Старые этапы остаются снимками только для просмотра.

Удаление из каталога использует реестр `batch_publications` и точный `external_id`. Для старых партий, созданных до появления этого реестра, external_id восстанавливается из текущих товаров и сохранённого снимка партии. Товар удаляется из Rails только когда он не встречается в другой партии или её историческом снимке; неоднозначные товары остаются защищёнными. Общие S3-фотографии также не удаляются.

Перед каждой публикацией показывается предпросмотр количества новых, обновляемых, пропускаемых и удаляемых товаров, а также исходных видео, которые действительно потребуется перенести в S3. Уже сохранённые в атрибутах партии или в Rails-видеосвязи S3-файлы в этот счётчик не попадают. Режим `Заменить каталог текущей версией` следует использовать только после проверки этого предпросмотра.

При публикации цена является источником истины для режима отображения цены:
положительная цена передаётся как `price_on_request: false`, а нулевая — как
`price_on_request: true`. Это значение записывается в Rails `metadata` и
перезаписывает устаревший флаг при обновлении существующего товара.

## Автопостобработка поставщика

В настройках поставщика можно назначить `post_process_script` и включить флажок `Автоматически`. После успешного сохранения сырого JSONB-снимка партия автоматически проходит тот же Python-скрипт, который доступен по кнопке вручную.

Если скрипт завершился ошибкой, сырая партия сохраняется, а ошибка записывается в лог; автоматический запуск не удаляет исходные товары.

## Значения поставщика и типовые атрибуты

По умолчанию поставщик получает атрибуты своей категории и подкатегории автоматически. Если категории поставщика не ограничены, AI дополнительно получает безопасный общий набор `sizes`, `size_system` и `measurements`, чтобы не потерять размеры смешанного альбома до определения итоговой категории. При необходимости в карточке поставщика можно перейти к ручному набору. Это схема для AI и парсинга: модель возвращает только подтверждённые значения, а отсутствующий атрибут полностью пропускается.

### Фильтры и характеристики

В админке есть отдельная страница `/admin/filter-characteristics` («Схема атрибутов»). Данные справочника хранятся в Rails CRM и являются единым источником для поставщиков, AI, редакторов товара и витрины:

- «Характеристика» — значение показывается в карточке товара;
- «Фильтр» — значение доступно для отбора товаров;
- «Вариант товара» — значение участвует в выборе варианта при добавлении в корзину;
- «Включён» — атрибут участвует в текущей схеме распознавания.

Для одежды и обуви размеры используются как фильтр и измерение варианта. Явная строка `Размеры: 38-40`, `EU 38, 39, 40` или `S, M, L` сохраняется в `catalog_attributes.sizes`; размерный ряд используется витриной для кнопок выбора. Отсутствие размеров не блокирует публикацию и не означает наличие на складе.

Если AI упомянул явный обувной размерный ряд в публичном описании, но не вернул `catalog_attributes.sizes`, сервер повторно извлекает размеры из результата. Это защищает карточку от потери вариантов из-за пропущенного JSON-поля.

Точные подписи (`Размеры`, `EU`, `Верх`, `Подкладка`, `Подошва`, `Высота каблука`) обрабатываются первым проходом. AI используется для неоднозначного текста и возвращает дополнительные значения в `attributes`; существующие значения не удаляются. Старые коды сопоставляются с каноническими: например, `bag_dimensions` → `dimensions`, `shoe_size_system` → `size_system`, а общий `material` у обуви → `upper_material`.

В таблице замеров размер хранится в `rows[].size`, поэтому пустая дублирующая колонка `size`/`Размеры` автоматически удаляется при нормализации AI-ответа вместе с её пустыми значениями. Остальные параметры замеров сохраняются.

Старые ID брендов и категорий поставщиков сопоставляются с каноническими Rails ID. В интерфейсе отображаются названия, а старые значения сохраняются в резервных полях. Перед запуском legacy-парсера канонический ID временно переводится обратно в ожидаемый старый ID, поэтому существующие Python-скрипты не требуют одномоментной переписывания.

Если точного соответствия нет (например, для старой подкатегории, которой пока нет в Rails), значение помечается как несопоставленное и не заменяется предположением.

## AI и атрибуты

AI получает только схему атрибутов, допустимую для категории конкретного товара. При сохранении результата совместимые существующие ключи объединяются с новыми значениями, а зарегистрированные атрибуты другой категории отбрасываются. Например, ювелирный `stones` не может попасть в обувь: стразы на обуви описываются как декор в тексте карточки. При включённой обработке фотографий описание дополняется подтверждёнными визуальными деталями формы, конструкции, фактуры, застёжки, подошвы, фурнитуры и декора.

Для опубликованного Rails-каталога структурированные характеристики хранятся в `catalog_attributes`. Их можно редактировать в карточке товара и искать через фильтр «Атрибуты» (ключ и, при необходимости, значение).

## Миграция базы

Для существующей базы применяется обычная миграция:

```bash
npm run db:migrate:scraping
```

Миграция добавляет `products.attributes` со значением по умолчанию `{}` и GIN-индексом. Существующие товары и CSV не изменяются.

После обновления справочников поставщиков один раз выполните:

```bash
npm run db:migrate:supplier-catalog-ids
```

Команда создаёт резервные legacy-поля, строит таблицу соответствий по названиям и родительским категориям и заменяет только однозначно найденные значения. Несопоставленные записи выводятся в отчёт и остаются без автоматической подстановки.

## Архитектурное решение

Внутри приложения каноническим источником партии является БД. Товары и история этапов хранятся в JSONB, а CSV используется только при явном ручном импорте или экспорте.

### Видео в опубликованной карточке

Видео поставщика хранится отдельно от фотографий в `video_url` и `video_poster_url`. При публикации AdminYeezy загружает подготовленный MP4 и WebP-постер в S3; постер не добавляется повторно в массив фотографий. В админской карточке видео отображается отдельным блоком с нативными контролами, а на основной витрине становится последней миниатюрой галереи.
