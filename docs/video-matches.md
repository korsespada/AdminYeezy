# Видео → товары

Раздел `/admin/video-matches` решает две задачи по одному и тому же поставщику:

1. **Видео → товары** — привязка видео из альбомов выгрузки к уже опубликованным
   товарам каталога (ниже).
2. **Карточки по правилам выгрузки** — обработка уже опубликованных товаров
   поставщика, которые не будут перевыгружаться: название, характеристики,
   описание и альты фото приводятся к правилам выгрузки ([раздел
   «Карточки по правилам выгрузки»](#карточки-по-правилам-выгрузки)).

## Видео → товары

Раздел привязывает видео поставщика к уже опубликованным
товарам каталога. Он нужен там, где выгрузка состоит из альбомов с видео
(«客订实拍»), а сами товары уже лежат в Rails CRM и пришли другим путём: у
альбомов и товаров нет общих идентификаторов, поэтому пара подбирается по
характеристикам, а решение принимает оператор.

## Данные и границы

- Источник альбомов — партия scraping-БД (`products` + `attributes.szwego_video_url`).
- Товары — опубликованный каталог Rails CRM; чтение и запись только через Rails API
  (`/admin/products`, `/admin/products/:id`). Прямая запись в CRM Postgres запрещена.
- Хранение очереди — таблицы `product_video_matches` и `product_video_match_scope`
  в `yeezy_scraping` (`npm run db:migrate:product-video-matches`).
- Видео переносится в собственный S3 теми же ключами, что и публикация выгрузок:
  `videos/{sha256(source_url)}.mp4` и `videos/{sha256(source_url)}-poster.webp`.
  Ключ детерминирован, поэтому повторный запуск ничего не перекачивает, а
  одинаковые видео из разных альбомов переиспользуют один файл.

## Пресеты

Сценарий целиком описан в `lib/video-match-presets.ts`: бренд каталога, поставщик
scraping-БД, имя поставщика в каталоге, партия выгрузки и список категорий,
которые считаются товарами этого поставщика. Пресет Hermes включает сумки на
плечо, сумки-мессенджеры, тоут, клатчи, кошельки и картхолдеры, косметички,
чемоданы, рюкзаки и поясные сумки.

## Сопоставление

`lib/video-match-fields.ts` разбирает характеристики с двух сторон:

- альбом: `Style：… Colour：… Size：A*B*Ccm Leather：… Hardware：…`;
- каталог: `Стиль: …`, `Цвет: …`, `Размер: …`, `Кожа: …`, `Фурнитура: …`.

Значения нормализуются: регистр, разделители размеров (`*`, `x`, `×`), приставка
«From France», русские и английские названия фурнитуры, порядок слов в модели
(«Kelly Mini 2» = «mini kelly 2»), коды цветов Hermes (`89/Noir` = `89/noir`).

Вес полей: стиль 40, цвет 25, размер 20, кожа 10, фурнитура 5. Уровни:

| Уровень | Балл | Смысл |
| --- | --- | --- |
| `exact` | 100 | совпали все пять характеристик |
| `strong` | 90–99 | совпали модель, цвет и размер, отличается кожа или фурнитура |
| `probable` | 70–89 | модель, цвет и размер совпали частично |
| `weak` | < 70 | в очередь не попадает |

Вариантом товара альбом считается только при совпадении модели и размера
(`isCandidate`). Одинаковые видео схлопываются: у товара остаётся один вариант на
файл, всего до `MAX_CANDIDATES_PER_PRODUCT` (5) вариантов; полное количество
хранится в `candidates_total`.

`product_video_match_scope` фиксирует все просканированные товары, включая те,
для которых вариантов не нашлось (`candidates = 0`) — иначе «нет совпадений»
невозможно отличить от «ещё не считали».

## Рабочий процесс

1. **Закрепить поставщика.** Товары категорий пресета получают
   `primary_supplier_id` поставщика с именем из пресета (Rails создаёт его при
   необходимости). Операция идемпотентна: товары с нужным поставщиком
   пропускаются, повторный запуск продолжает с места остановки.
2. **Собрать совпадения.** Клиент идёт по страницам каталога (по 100 товаров на
   категорию и статус) и после каждой страницы перезаписывает варианты, сохраняя
   уже принятые решения оператора. Архивные товары обрабатываются вторым проходом.
3. **Ревью.** Карточка показывает превью видео альбома и первое фото товара,
   сравнение по пяти характеристикам и переключатель вариантов. Апрув одного
   варианта снимает апрув с остальных вариантов того же товара.
   Массовый апрув работает по выбранным уровням уверенности, отдельной кнопкой —
   только по товарам с единственным вариантом.
4. **Загрузка.** Апрувнутые пары уезжают в S3 и патчат карточку товара
   (`video_url`, `video_poster_url`). Заливка идёт **на сервере**, а не во вкладке:
   кнопка переводит запуск в `running`, а работу ведёт супервизор приложения
   (`instrumentation.ts` → `lib/video-match-apply.ts`), который раз в десять секунд
   проверяет таблицу запусков и держит по одной задаче на партию. Поэтому заливка
   продолжается после перезагрузки страницы и после перезапуска контейнера, а
   вкладку можно закрыть. Состояние и прогресс — в `product_video_match_runs`
   (статус, размер порции, счётчики привязанных, сбоев и нечитаемых источников,
   heartbeat); страница подтягивает их опросом. Остановка — кнопкой, цикл
   завершает текущую порцию.

   Сбой одной строки не роняет цикл: применение повторяется до трёх раз с паузами,
   в конце запуска упавшие строки один раз возвращаются в очередь автоматически, а
   «Повторить ошибки» доступно вручную. Ролики, которые поставщик отдаёт битыми
   (полный файл без `moov`, пустой ответ, 404), помечаются отклонёнными с причиной
   «Источник нечитаем»: повторять их бессмысленно, у товара нужно выбрать другой
   вариант видео.

Статусы строки: `pending` → `approved` → `applied`, либо `rejected` / `failed`.

## Ограничения и известные особенности

- Поставщик публикует несколько альбомов на одну и ту же комбинацию
  характеристик, поэтому «один вариант» — редкость: у большинства товаров 5+
  видео-вариантов с одинаковыми характеристиками. Массовый апрув по уровню
  `exact` берёт самый свежий альбом; визуальная проверка остаётся за оператором.
- 4067 альбомов выгрузки (обувь, сервисные карточки) не содержат блока
  характеристик и в сопоставление не попадают.
- Видео скачивается из источника (xcimg.szwego.com) целиком, перекодируется
  ffmpeg в mp4 ≤ 1080p и получает постер; один файл занимает 5–11 МБ, время
  обработки — около 15 секунд на видео.
- Раздел не публикует товары и не меняет описания, цены и категории.

## Карточки по правилам выгрузки

Вторая задача раздела: привести уже опубликованные товары поставщика к правилам
выгрузки, когда перевыгрузка не планируется. Работает поверх каталога Rails и не
использует выгрузки и альбомы.

- Пресет — поставщик каталога и его категории (`lib/product-card-presets.ts`).
  Для Hermes это 9 «сумочных» категорий и 11 обувных, фильтр Rails
  `supplier=<uuid>` (по имени фильтр не работает), статус `active`; архив не
  обрабатывается.
- Очередь — `product_card_updates` в `yeezy_scraping`
  (`npm run db:migrate:product-card-updates`). Одна строка = один товар; хранится
  снимок текущей карточки (название, описание, характеристики, медиа с альтами),
  предложение, предупреждения, отдельный статус ИИ-текста и решение оператора.
  Повторный скан обновляет только строки `pending`, поэтому решения не сбрасываются.
- Разбор и сборка — `lib/hermes-card-facts.ts`, `lib/hermes-card-build.ts`,
  `lib/hermes-card-slug.ts`: название = тип изделия + модель + размер + материал +
  цвет Hermes («Сумка Birkin 25 см Swift 89/Noir», «Сумка Lindy 26 см Clemence
  18/Etoupe», «Клатч Chaine D'Ancre To Go 20.5 см Evercolor 8U/Blue Glacier»),
  тип берётся из категории каталога, русское название цвета согласуется с типом
  («Сандалии Oran шерсть оранжевые»). Размер в названии пишется с «см», чтобы не
  сливался с цветом-кодом, и только если он был в исходном названии: если размера
  там не было, карточка подразумевает один размер и число не придумывается.
  Материал в названии — латинская кожа Hermes («Swift», «Togo», «Clemence»,
  «Taurillon Regate») или базовое слово («кожа», «замша», «шерсть»); длинные
  формулировки остаются в характеристиках. `model_name` без размера,
  `hardware_color` из «Фурнитуры» (легаси-ключ `hardware` переливается), для сумок
  `dimensions` «25 × 20 × 13 см» плюс `bag_width_cm`/`bag_height_cm`, для обуви
  `upper_material`/`sole_material`/`lining_material`/`heel_height` при
  подтверждении, `colors`, `materials` и `sizes` сохраняются. Материал берётся из
  блока «Материал»/«Кожа», а если блока нет — собирается из текста описания
  («из кожи taurillon Regate и холста H canvas» → «Кожа Taurillon Regate»,
  «Холст H canvas»). Цвет пишется в два атрибута: `colors` — обычный цвет без кода
  («Черный», «Etoupe», «Noir»), `supplier_color` — «Цвет поставщика» в форме
  Hermes («18/Etoupe», «ck89/Noir», «37/Gold»). Атрибут `supplier_color`
  зарегистрирован в реестре Rails (характеристика, не фильтр) и в
  `lib/catalog-attribute-schema.ts`; когда поля «Цвет» нет, цвет ищется в тексте
  («в бордовом цвете» → «Бордовый»). Для обуви из размерного ряда заполняются
  `sizes` (`{groups:[{system:'EU',values,audience}],values}`, пол из карточки) и
  `size_system`, если их не было. Материал подошвы пишется только по резине,
  каучуку, полиуретану или пластику: кожаной подошвы не бывает, «внутренняя
  подошва» — это стелька.
- Значения блока обрезаются по встроенному ключу: у части карточек весь блок
  идёт одной строкой («Цвет: Red Материал: Кожа Размер: …»), иначе мусор уезжает
  в название и адрес. Если цвет назван по-русски вместе с внутренним цветом
  Hermes в скобках, в название и адрес идёт внутренний цвет: «Черный (ck89/noir)»
  → `ck89/Noir`, «Raisin (виноградный фиолетовый)» → `Raisin`. Артикул цвета без
  имени («Золотисто-коричневый (CK37)») сохраняется вместе с русским названием,
  а латинское имя с кодом («Blue izmir (7W)») собирается в форму каталога
  `7W/Blue Izmir`. Переводы из скобок остаются для описания.
- Повторный скан обновляет снимок карточки, название, адрес и характеристики,
  но не перетирает готовый ИИ-текст (описание и альты) и не сбрасывает решения
  оператора: обновляются только строки в статусе `pending`, а при `ai_status = ready`
  описание и альты сохраняются.
- Адрес — `hermes-{модель}-{размер}-{цвет}-{фурнитура}-{материал}-{артикул}`,
  значения латиницей из описания, транслитерация как в Rails, обрезка до 160
  знаков с сохранением артикула. У мультицветных моделей в адрес идёт первый код
  и первое имя цвета. Тип изделия («Сумка», «Клатч») в адрес не входит: он есть
  в названии, а адрес остаётся в согласованном формате.
- Применение — `lib/product-card-apply.ts`: сначала `PATCH /admin/products/:id`
  (название, характеристики, альты фото), затем явный адрес отдельным
  вызовом `POST /admin/products/:id/set_slug`, который закрепляет его флагом
  `slug_locked` (см. `docs/rails-integration.md`). Описание заменяется только
  готовым ИИ-текстом: черновик из фактов короче текущего публичного текста
  и в Rails не уходит, поэтому товар без ИИ-прохода сохраняет своё описание.
  Медиа берётся из свежей карточки Rails, альты подставляются по совпадению
  URL, поэтому новые фото не теряются. Если название в каталоге уже не совпадает
  со снимком сканирования (карточку правили после скана), применение
  останавливается с понятной ошибкой: строку нужно пересобрать и проверить
  заново, чужие правки не перезаписываются. Статусы строки: `pending` →
  `approved` → `applied`, либо `rejected` / `failed`.
- До апрува оператора в Rails не уходит ни один запрос.
- ИИ-проход (`lib/product-card-ai.ts`) даёт полное описание, альты и материалы:
  contact sheet 3×3 из фотографий карточки Rails, один запрос на товар, ответ
  строго `{description, photo_alts, materials}`. Описание — публичный текст
  900–1800 знаков: баланс подтверждённых фактов исходной карточки и видимых на
  фотографиях деталей (силуэт, ручки и ремень, клапан и замок, швы, фактура кожи,
  дно и ножки, подкладка). Альты нормализуются к числу фотографий (60–120 знаков,
  жёсткий максимум 160), реклама, эмодзи, «заказ клиента», цены и условия
  возврата не переносятся. Материалы из ответа дополняют характеристики, если там
  пусто. Провайдер и модель — те же, что в «Выгрузках» (`/admin/ai-rules`); при
  ошибке провайдера строка получает `ai_status = failed` и текст ошибки, черновик
  описания остаётся. Локальная проверка идёт ключом группы Gemini
  (`BYESU_GEMINI_API_KEY` в `.env.local`, файл в `.gitignore`): без него модель
  `gemini-3.8-flash-high` недоступна и запрос уходит в OpenRouter.
- Комплектация и упаковка — отдельный текст поставщика (оранжевая коробка,
  защитный бокс, пыльник, бутиковый сет). Он добавляется к описанию отдельным
  абзацем детерминированно, а модель про упаковку не пишет вообще, поэтому абзац
  одинаков у всех товаров и правится в одном месте.
- Промпт поставщика хранится в `product_card_supplier_settings` (та же миграция,
  поля `ai_prompt` и `packaging_text`) и правится прямо в разделе кнопкой
  «Промпт поставщика»: он добавляется к базовым требованиям и общим правилам
  каталога. Пока своего текста нет, используется подсказка пресета — для Hermes
  она перечисляет его особенности (внутренний цвет вида `18/Etoupe`, модель без
  размера, точные кожи и фурнитура, габариты сумок и размерный ряд обуви, что не
  переносится из исходного текста). Кнопки в редакторе возвращают подсказки
  Hermes, очищают тексты или показывают действующие.
- Интерфейс — вкладка «Карточки по правилам выгрузки» на `/admin/video-matches`
  (`components/video-matches/ProductCardsApp.tsx`), устроена как «Выгрузки»:
  сначала список поставщиков с прогрессом (в очереди, ждут решения, ИИ
  обработано/ждёт/ошибки, спорные), затем открытие поставщика — карточки
  «сейчас / станет» с фильтрами по статусу, типу товара, состоянию ИИ и поиску.
  На карточке видно бейдж ИИ (готово с моделью, ждёт, ошибка), характеристики,
  описание и альты. Кнопки: «Собрать карточки», «ИИ по всем», «ИИ» (по выбранным
  или по нескольким следующим), «Апрувить без спорных», «Применить апрувнутые»,
  «Очистить несогласованные». Скан, ИИ и применение идут порциями по кнопке,
  поэтому длинная операция не держит запрос.
- Прогон ИИ по всем карточкам — кнопка «ИИ по всем» (`lib/product-card-ai-run.ts`).
  Прогон живёт в фоновом супервизоре (`instrumentation.ts`), а не в запросе:
  очередь читается порциями по `batch_size`, прогресс и признак жизни цикла
  пишутся в `product_card_ai_runs`, поэтому вкладку можно закрыть, а после
  рестарта контейнера прогон поднимается сам. Интерфейс раз в пять секунд
  показывает «обработано / ошибок / осталось / модель», рядом кнопка «Пауза ИИ».
  Упавшие строки возвращаются в работу один раз, лимит прогона — 12 часов.
  Скорость задаёт провайдер: BYESU `gemini-3.8-flash-high` даёт 10–30 секунд на
  товар, то есть 2,2 тысячи карточек — это несколько часов фоновой работы.

## Проверки

```powershell
npm run db:migrate:product-video-matches
npm run db:migrate:product-card-updates
npx vitest run __tests__/unit/lib/video-match-fields.test.ts
npx vitest run __tests__/unit/lib/hermes-card.test.ts __tests__/unit/lib/product-card-apply.test.ts
npx vitest run __tests__/unit/lib/product-card-ai.test.ts __tests__/unit/components/ProductCardsApp.test.tsx
```

Сборка совпадений идемпотентна: повторный запуск на той же выгрузке даёт то же
количество строк, а решения оператора сохраняются.
